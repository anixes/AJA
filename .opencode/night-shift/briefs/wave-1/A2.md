# NIGHT-SHIFT WAVE 1 — A2 Brief: Async/Event-Loop Audit
Scope: `aja/orchestration/` (gateway.py, direct_loop.py, direct_session.py, swarm.py, activity_rt.py, adapters.py, context_window.py, tools/*, providers/*) + `aja/llm.py`. READ-ONLY audit — no production code changed.

---

## Findings

### F1. CRITICAL — Per-call provider adapters are never closed: leaked httpx/aiohttp connection pools on EVERY LLM call
- **File:line**: `libs/aja-core/aja/orchestration/gateway.py:311-336` (adapter instantiation at :316); `providers/openai_compat.py:135-157` (`_client` never closed); `providers/google_adapter.py:72-75` and `providers/anthropic_adapter.py:42-51` (per-instance `aiohttp.ClientSession`); `providers/__init__.py:33-47` (all providers registered → this path is the default for openai/openrouter/copilot/llama_cpp/google/anthropic).
- **Description**: `LLMGateway.chat()` constructs a **fresh adapter instance per call** (`adapter = adapter_cls(api_key=..., base_url=...)`) and never calls `await adapter.close()`. Each `OpenAICompatAdapter` lazily builds an `AsyncOpenAI` (wrapping an `httpx.AsyncClient` pool with keep-alive connections); each `GoogleAdapter`/`AnthropicAdapter` builds an `aiohttp.ClientSession`. Since the instance is discarded after the call, the client/session is abandoned unclosed. Under `aja serve` (Phase 12 24/7 deployment), every chat/stream/embed call leaks a socket + connection-pool object → fd exhaustion, `ResourceWarning: unclosed ...` noise, and the documented "Task exception was never retrieved / Event loop is closed" GC-cleanup storms on Windows (see Internet research R1/R2).
- **Repro sketch**: loop 200 × `await gw.chat(...)` against a local llama.cpp server; watch `netstat` handle count / `ResourceWarning`s grow monotonically.
- **Proposed fix**: cache one long-lived adapter per gateway (like `self._openai_client`) keyed by `(api_key, base_url)`; close it in `LLMGateway.close()`. Alternatively wrap per-call usage in `async with` context-manager support (all three adapters already expose `close()`).

### F2. HIGH — Native tool execution blocks the event loop for up to 120s inside `async def` (`ActivityRuntime._run_python`)
- **File:line**: `orchestration/activity_rt.py:284-298` (`registry.execute(...)` sync call at :288); blocking implementations in `tools/native.py:823` (`time.sleep`, unbounded by tool contract beyond arg), `tools/native.py:863` (`subprocess.run(..., timeout=120)`), `tools/web_tools.py:35/:84` (`urllib.request.urlopen` 10–15s), `tools/native.py:1034` (urllib 15s). Aggravated by `scheduler.py:111-114`: the "Parallel"ActivityScheduler runs PYTHON activities under a semaphore via `asyncio.gather` — but since each blocks the loop synchronously, they serialize AND freeze every other coroutine (heartbeats, telemetry tails, gateway adapters).
- **Description**: All `NativeToolRegistry` tools are synchronous (subprocess/urllib/file IO/sleep). `_run_python` is `async def` but invokes them inline — no `asyncio.to_thread`. A single LLM-emitted `run_shell_command` stalls the whole process for up to 120s; a `sleep(60)` tool call freezes the event loop completely.
- **Repro sketch**: mission where worker emits `sleep(30)` while a Telegram/Discord telemetry tail is connected → all platform heartbeats stop for 30s.
- **Proposed fix**: `await asyncio.to_thread(registry.execute, activity.tool, activity.args)` in `_run_python` (keep the semaphore for concurrency limiting).

### F3. HIGH — Blocking subprocess workers (incl. multi-minute pytest) called directly inside async `dispatch_worker`
- **File:line**: `orchestration/adapters.py:25-43` (`return adapter.run(baton, workspace_dir)` at :43 is sync); blocking work in `adapters.py:50-110` (`_create_branch`, `_get_diff`, `_run_tests` → `subprocess.run([..., "pytest", ...])` with NO timeout at :89-109), plus CLI adapters (:169, :197, :226, :255).
- **Description**: `dispatch_worker` is `async def`, but for any non-native worker id it calls the synchronous `BaseAdapter.run()` inline — git checkouts, full CLI agent runs, and unit-test suites run on the event loop thread. `_run_tests` has no timeout: a hung pytest wedges the orchestrator forever.
- **Repro sketch**: dispatch `worker_id="test-worker"` → `TestAdapter.run` does blocking `subprocess.run`; concurrent gateway/cron ticks freeze until the subprocess exits.
- **Proposed fix**: `return await asyncio.to_thread(adapter.run, baton, workspace_dir)`; add `timeout=` to `_run_tests`.

### F4. HIGH — Sync-over-async bridge blocks the running loop: `ToolExecutor.execute` from async `run_direct_loop`
- **File:line**: `orchestration/tools/executor.py:37-56` (`thread.join()` at :53 when a loop is already running); call site `orchestration/direct_loop.py:270` (`result = executor.execute(cmd)` inside `async def run_direct_loop`). Same pattern family as `llm.py:150-176` (`run_async_synchronously`, `t.join()` at :175) used by all five `*ModelProvider.chat_completions` classes (`llm.py:201, 243, 285, 327, 422`).
- **Description**: When invoked from within a running loop (the direct-mode loop always is), the code spawns a thread that runs a *second* event loop and then **blocks the caller's loop** with `thread.join()` until the shell command finishes (timeout=30s per command). The whole process — LLM streams, schedulers, TUI, gateway adapters — stalls per bash command. It also silently creates+sets a global event loop per worker thread and never closes the caller-side state cleanly if the future raises. `run_async_synchronously` has the identical hazard: any future call of `completion()` / provider `.chat_completions()` from an async context blocks the loop for full LLM latency (retries × exponential backoff).
- **Repro sketch**: `SwarmEngine.execute_direct("run pytest")` with 5 bash turns → measure event-loop lag (e.g., a concurrent `asyncio.sleep`-based heartbeat task misses ~150s of beats).
- **Proposed fix**: make the direct-loop path await-native: add `async execute_async()` on ToolExecutor using `get_default_execution_manager().run(...)` directly (no thread hop), and have `run_direct_loop` call it. Keep the sync bridge only for true sync callers.

### F5. MEDIUM/HIGH — Loop-switch logic abandons unclosed sessions and hijacks the thread's global event loop
- **File:line**: `gateway.py:215-228` (`_get_session`), `gateway.py:237-257` (`_get_openai_client`), `providers/openai_compat.py:135-157`.
- **Description**: Two problems. (a) On loop change (`self._session_loop != loop`), the old `aiohttp.ClientSession` is simply replaced — never `await .close()`d → connector/socket leak (same leak class as F1). (b) The no-running-loop branch executes `loop = asyncio.new_event_loop(); asyncio.set_event_loop(loop)` as a side effect of a getter — mutating global asyncio state from library code. Combined with multiple short-lived loops (tests, `run_async_synchronously` threads, `asyncio.run` entrypoints) this reproduces the canonical `RuntimeError: Event loop is closed` failures documented for AsyncOpenAI/httpx when clients cross loops (R1/R2). Note the guard compares identity with the *current* loop, so a session created in a since-closed loop is detected late — first request after switch may still hit the abandoned-connector path.
- **Repro sketch**: create `LLMGateway(provider="copilot")`; call `_google_generate_content` under `asyncio.run(A)`; then `asyncio.run(B)` repeatedly → intermittent closed-loop errors + ResourceWarnings.
- **Proposed fix**: close the old session before replacing (`old = self._session; ...; if old: await old.close()` — needs an async factory); remove `set_event_loop` side effects (require a running loop, else raise or use a dedicated loop owned by the gateway).

### F6. MEDIUM — `SwarmEngine.plan_and_execute_batons` performs heavy sync work on the loop
- **File:line**: `swarm.py:217-228` (`get_text_embedding` — may lazy-load ONNX/SentenceTransformer; LanceDB `query_territory`), `swarm.py:230-238` (skill store search), `swarm.py:320/:395-399/:456` (`write_baton`/`read_baton` pyarrow file IO), `swarm.py:472` (`run_verification` — sync checks possibly spawning processes).
- **Description**: First-call embedding model load can block tens of seconds; LanceDB round-trips ~34ms each but scale; verification can be arbitrarily slow. All inside the orchestrator's async path.
- **Proposed fix**: wrap each in `asyncio.to_thread`.

### F7. MEDIUM — DirectSession: LanceDB mirroring, recall embedding, and compression executed inline on the loop
- **File:line**: `direct_session.py:116-127` (`_mirror` → `mirror_chat_message` LanceDB write, called from async `_turn` at :271/:309), `direct_session.py:276-286` (`hybrid_recall` — embedding compute + journal scan, sync), `direct_session.py:313-318` (`compress_history` — fine, cheap heuristic, LOW), `direct_session.py:366-371` (sync `prompt_session.prompt` — acceptable in a REPL but starves background tasks during idle input).
- **Proposed fix**: `to_thread` for mirror + recall.

### F8. MEDIUM — Anthropic adapter retries non-retryable 4xx with zero backoff
- **File:line**: `providers/anthropic_adapter.py:200-221`.
- **Description**: Any status ≥400 raises `RuntimeError`, which the retry loop re-attempts immediately (no `asyncio.sleep`, no status discrimination — unlike `openai_compat._NON_RETRYABLE_STATUS`). A 401 burns all retries instantly; a 400 is retried identically. Also `stream()` (:223-231) fakes streaming off `chat()` — consistent with Google adapter but worth documenting.
- **Proposed fix**: skip retry on 400/404/422 (match openai_compat), add exponential backoff.

### F9. LOW/MEDIUM — Streaming paths don't deterministically close the OpenAI stream on early exit/fallback
- **File:line**: `gateway.py:685-691` (`chat_stream`), `providers/openai_compat.py:285-299` (`stream`).
- **Description**: `response_stream = await client.chat.completions.create(**kwargs)` is consumed with a bare `async for`. If the consumer aborts (GeneratorExit) or an exception mid-stream triggers the non-streamed fallback, the SSE response is left to GC — producing the well-known "Event loop is closed" cleanup noise on Windows and delayed socket release. llama.cpp server keeps generating unless disconnected (its resumable-SSE feature notwithstanding), so leaked streams waste local GPU cycles.
- **Proposed fix**: `async with await client.chat.completions.create(...) as stream:` (SDK supports async CM) or explicit `try/finally: await response_stream.close()`.

### F10. LOW — Copilot 401 retry `continue` skips backoff; tight refresh loop possible
- **File:line**: `gateway.py:520-531`.
- **Description**: On 401/403 the Responses-API path refreshes the token and `continue`s without sleeping; if `resolve_copilot_token()` keeps returning the same stale token, all retries burn in a hot loop (network-bound). Legacy except-path (:628-642) sleeps correctly.
- **Proposed fix**: `await asyncio.sleep(min(2**attempt, 8))` before `continue`.

### F11. INFO (adjacent, security) — API key passed on worker command line
- **File:line**: `swarm.py:184-189` (`--key", self.gateway.api_key` in `_run_agent_sync` argv).
- Visible in process listings (`ps`/Task Manager). Not strictly async, flagged for Wave-2 security pass.

**Checked and clean**: no un-awaited coroutines found; the single `create_task` (`scheduler.py:59`) retains references and results are reaped via `asyncio.wait`+`gather(return_exceptions=True)`; retry sleeps elsewhere use non-blocking `await asyncio.sleep(2**attempt)`; `context_window.py` is pure-CPU and cheap; `direct_loop.py` itself is clean apart from F4's executor call.

## Internet research

Verified contracts & pitfalls (all accessed 2026-08-25):

- **R1. aiohttp ClientSession lifecycle**: persistent-session-per-app guidance; sessions must be closed; per-loop ownership ("If you use your library with multiple asyncio loops — please use a ClientSession per loop at least, everything hangs otherwise"); graceful-shutdown sleep caveat.
  - https://docs.aiohttp.org/en/stable/client_advanced.html (Graceful Shutdown, Persistent session)
  - https://github.com/aio-libs/aiohttp/issues/3954 (maintainer quote on session-per-loop)
  - https://github.com/aio-libs/aiohttp/pull/13429 (cross-thread/eager-start "attached to a different loop" hazard)
- **R2. openai-python AsyncOpenAI lifecycle**: creating clients per iteration / sharing across loops causes `RuntimeError: Event loop is closed` (Windows Proactor) and `Task exception was never retrieved` from httpx `aclose()` GC cleanup; official remedy = one shared client OR async context manager OR explicit `await client.close()`.
  - https://github.com/openai/openai-python/issues/1254
  - https://github.com/openai/openai-python/pull/1262 (async CM rationale)
  - https://github.com/openai/openai-python/issues/1777 (client shared across event loops → APIConnectionError)
  - https://github.com/encode/httpx/discussions/2489 ("Don't share an AsyncClient across multiple event loops")
  - https://sewon.dev/en/place2page-openai-async-client-event-loop-closed/ (case study: close-in-same-loop discipline)
- **R3. llama.cpp server**: `/v1/chat/completions` is OpenAI-compatible incl. `"stream": true` SSE and tool calling; native `/completion` is NOT OAI-compatible; streaming generations abort on socket drop (resumable SSE is opt-in via `X-Conversation-Id`) — so leaked/unread streams keep GPU work alive.
  - https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md
  - https://llama.app/docs/api
- **R4. urllib/subprocess blocking semantics**: standard-library `urllib.request.urlopen`/`subprocess.run` are fully blocking (no async surface) — basis for F2/F3/F6 classification. (Python docs: https://docs.python.org/3/library/urllib.request.html, https://docs.python.org/3/library/subprocess.html)
- Provider adapter APIs cross-checked: Copilot Responses API path (`/v1/responses` payload building in gateway.py:493-562) matches OpenAI Responses wire format; Google generativelanguage REST shape matches google_adapter translation.

## Proposed claims (for council coordination)

1. **CLAIM(A2-F1)**: Introduce cached, closable adapter instances in `LLMGateway` (lifecycle-managed alongside `_openai_client`). Highest ROI single fix in scope.
2. **CLAIM(A2-F2)**: One-line `asyncio.to_thread` in `ActivityRuntime._run_python` (+ optionally executor dispatch path). Must coordinate with whoever owns scheduler concurrency tests (semaphore semantics unchanged).
3. **CLAIM(A2-F4)**: Add async-native execution to `ToolExecutor` and switch `run_direct_loop` to it; deprecate thread-hop bridge for async callers.
4. **CLAIM(A2-F5)**: Session/client replacement must close-before-replace; delete `set_event_loop` side effects. Touches same lines as F1 fix — bundle them.
5. Leave F6–F10 as fast-follow small patches; F11 route to the security subgroup.

## Council questions

1. **F1 blast radius**: Is any code path depending on per-call fresh adapters picking up rotated Copilot tokens mid-mission? Cached adapters need the token-refresh invalidation hook (`_refresh_copilot_auth` already nulls `_client` — confirm parity at the gateway level).
2. **F2 policy**: Should blocking native tools be `to_thread`'d unconditionally, or do Windows ConPTY/process-heavy paths assume same-thread execution anywhere (PTY tests pin xdist groups)? Needs an owner of `runtime/execution` to sanity-check.
3. **F4**: Direct mode currently serializes commands intentionally? If yes, keep serialization via an `asyncio.Lock` around the new async executor rather than relying on accidental loop-blocking.
4. **Backpressure**: With F2 fixed, `ParallelActivityScheduler` python activities become truly parallel — is `concurrency_limit=4` safe against tools that mutate shared workspace files concurrently?
5. **Sync facade strategy**: `aja.llm.completion()` / provider `.chat_completions()` remain sync bridges. Do we bless them for thread-pool-only use (document + enforce via lint rule) or plan an async-first migration? Affects planner (`decompose`) which is deliberately sync.
