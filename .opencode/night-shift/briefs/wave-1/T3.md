# T3 — Type-Contract Hunt Brief (memory/ skills/ planning/)

Read-only audit. Scope: `libs/aja-core/aja/memory/*`, `aja/skills/{skill_store,skill_executor,skill_compiler}*.py` (note: skill_compiler lives at `aja/cognitive/skill_compiler.py`), `aja/planning/*`. All line numbers verified 2026-08-25.

## Findings

### F1 — HIGH · planning/failure_memory.py:96 (reader) vs planning/react_executor.py:319–326 (writer)
**Description:** `get_failure_penalty()` does `set(f["plan_node_ids"])` and `cosine_similarity(goal_emb, f["goal_embedding"])`. But the in-loop failure record written by ReActExecutor (`react_executor.py:319`) contains keys `goal/node/state/plan_embedding/error/failure_type` — **no `plan_node_ids`** → guaranteed `KeyError`. Only the escalation-path writer (`react_executor.py:479–486`) includes it.
**Data-origin trace:** Writer A (wave-loop failure): omits `plan_node_ids`. Writer B (escalation): includes it. Reader assumes every persisted record has it. Additionally `goal_embedding` values persisted across an embedding-backend/model switch have mismatched dims → `cosine_similarity` raises `ValueError("Vectors must have the same dimensionality.")` (`embeddings/similarity.py:22-23`) which propagates out of the reader.
**Severity caveat:** `get_failure_penalty()` currently has no callers (grep: only definition), so this is latent-but-guaranteed the moment Phase 14 penalty wiring lands.
**Proposed guard:** `f.get("plan_node_ids") or []`; wrap cosine call in try/except ValueError→skip; normalize records on load.

### F2 — HIGH · skills/skill_executor.py:543,598 (+ skill_composer.py:137,242; skills/tool.py:57)
**Description:** Reader/writer column-contract break. `SkillStore` rows expose `skill_id`, `tool_sequence_json`, `tags_json` (`skill_store.py:78-98`). But `execute_skill()` reads `skill.get("id", "unknown")`, `skill.get("tool_sequence")`, `check_environment()` reads `skill.get("prerequisites")` — **none of these keys exist in stored rows**. The docstring says the dict comes from `recommend_skill()`, which would normalize names — but `recommend_skill` is defined **nowhere in the repo** (grep confirmed). `skill_composer.py:137` does `from aja.skills.skill_store import recommend_skill` → ImportError at runtime. Same latent gap for `mark_skills_stale` / `touch_skill` imported by `skill_executor.py:98,110` (those two are exception-wrapped, so they silently no-op).
**Data-origin trace:** Writer stamps `tool_sequence_json` (skill_store.py:137); readers assume a post-normalization shape that no code produces. Any caller passing `SkillStore.get_skill()` output into `execute_skill()` gets `tool_sequence=[]` → immediate `SKILL_EXECUTION_FAILED "empty tool_sequence"` fallback.
**Proposed guard:** Implement `recommend_skill()` (or a `_normalize_skill_row()` in SkillStore) mapping `skill_id→id`, `tool_sequence_json→tool_sequence` (decoded), `tags_json→tags`; fix the composer import.

### F3 — MEDIUM · memory/vector.py:76
**Description:** `rec_metadata = json.loads(row["metadata"])` is completely unguarded. The `metadata` column is a nullable string; LanceDB/pyarrow `to_pylist()` returns Python `None` for null cells. `json.loads(None)` raises `TypeError` — one null row kills the entire `search()` for all consumers (gateway recall, orchestrator).
**Data-origin trace:** Only `VectorMemory.add()` writes this table today and always stamps `json.dumps(...)`, so nulls require legacy/pre-stamping rows or external writers — plausible given the table predates model stamping (the file itself carries legacy-row handling at :84-86, proving legacy rows exist). This is exactly checklist items #1+#2 combined.
**Proposed guard:** `raw = row.get("metadata"); rec_metadata = json.loads(raw) if isinstance(raw, str) and raw.strip() else {}`.

### F4 — MEDIUM · planning/react_executor.py:390–397 vs plan_store.py:115
**Description:** `_record_repair()` calls `PlanStore.record_repair(plan_id=…, node_id=…, attempt=…, failure_kind=…, action_taken=…, notes=…)`, but the actual signature is `record_repair(plan_id, node_id, action, metadata=None)` → `TypeError: unexpected keyword argument 'attempt'` on **every** invocation, silently swallowed by the surrounding `except Exception` → repair telemetry is never persisted to `core_tool_executions`.
**Data-origin trace:** Signature drift between Phase 11 design and current PlanStore; the broad except masks it permanently.
**Proposed guard:** Align call site with signature (pack extras into `metadata=`), and log swallowed exceptions instead of print-and-continue.

### F5 — MEDIUM · cognitive/skill_compiler.py:99,132,170
**Description:** Same crash class as the recently fixed `model=None → .startswith`: `trajectory.domain.lower()` (:99) crashes with AttributeError if domain is None (line :112 guards it with `or "general"`, :99 does not). `step.action_payload[:80]` (:132) and `[:40]` (:170) raise TypeError when payload is None — legal because `TrajectoryStep.action_payload: Any` has no non-None guarantee (`cognitive/memory_models.py:52`).
**Data-origin trace:** Trajectories are rehydrated from episodic JSON (`save_episode` writes `str(s.action_payload)` so disk round-trip is safe), but in-process construction sites pass raw values (e.g., ttc_planner passes `branch.description`; any future caller passing None hits this). Domain default `"general"` protects only omission, not explicit None.
**Proposed guard:** `(trajectory.domain or "general").lower()` and `str(step.action_payload or "")[:80]`.
**AST note (checklist #5):** `_validate_skill` catches only `SyntaxError` from `ast.parse(script_code)`; since CPython 3.12 null bytes also raise SyntaxError (previously ValueError), and `UnicodeEncodeError`/`OverflowError` are theoretically possible for exotic source — script_code is compiler-generated strings, so risk is acceptable, but `except (SyntaxError, ValueError)` would be strictly safer.

### F6 — LOW · planning/method_store.py:108–113 + method_pruner.py:112–124 + method_retriever.py:52–53
**Description:** `MethodStore.load()` backfills missing embeddings via `EmbeddingService().embed(...)` — but EmbeddingService is now **fail-loud** (`OnnxBackendUnavailable`, service.py:359-370). A corrupt/partial methods.json migrated while the real backend is down makes `load()` raise → `retrieve_methods()` raises → planner degrades to fallback graph (caught upstream in decompose per-mode try/except). Separately, embeddings persisted in methods.json under one model then loaded under another dim would make `VectorIndex.search` / `_deduplicate` raise `ValueError` from `cosine_similarity` — currently all registered models are 384-dim, so low likelihood, zero guard.
**Data-origin trace:** methods.json is a JSON file with no model stamping (unlike LanceDB tables, which stamp embedding_model provenance) — cross-model mixing is undetectable at read time.
**Proposed guard:** Wrap per-method embed backfill in try/except (skip + warn); stamp `embedding_model` per method and skip mismatches like VectorMemory does.

## Internet research
- https://github.com/apache/arrow/issues/50327 — pyarrow `to_pylist()` semantics: built on `GetScalar` + `as_py()`; null scalars convert to Python `None`. Confirms null columns surface as `None` dict values, never omitted.
- https://arrow.apache.org/docs/python/generated/pyarrow.ListArray.html — official `to_pylist()` docs ("Convert to a list of native Python objects"; nulls→None).
- https://github.com/lancedb/lance/issues/4385 — Lance nullability handling; null struct/list cells round-trip as null (older versions coerced null lists to `[]` — relevant to vector-column assumptions on legacy files).
- https://github.com/lancedb/lance/issues/1946 — historical bug where list-column nulls were replaced with `[]` on write; legacy files cannot recover nulls — supports treating old vector cells defensively.
- https://docs.python.org/3/library/ast.html — `ast.parse` raises `SyntaxError` on invalid source.
- https://github.com/python/cpython/issues/122461 — since 3.12, null-byte source raises `SyntaxError` (not documented `ValueError`) in `ast.parse`/`compile`; plus tracker notes on `UnicodeEncodeError`/`RecursionError` edge cases (bugs.python.org/issue30637 thread).

## Proposed claims
1. T3-C1: `FailureMemory.get_failure_penalty` crashes on records written by the wave-loop path (missing `plan_node_ids`) — deterministic KeyError, writer/reader mismatch.
2. T3-C2: The skill execution pipeline's key normalization layer (`recommend_skill`) does not exist anywhere; store↔executor column names (`*_json` suffixes, `skill_id`) never match reader expectations.
3. T3-C3: `PlanStore.record_repair` has been called with an incompatible kwargs set forever; its except-swallow hides that zero repair telemetry was ever recorded.
4. T3-C4: `VectorMemory.search` dies wholesale on the first null/malformed metadata cell (unguarded json.loads).

## Council questions
1. Should fail-loud `EmbeddingService` be allowed inside lazy migration/backfill loops (`MethodStore.load`, `reindex_embeddings`), or should migration paths get explicit try/except + skip? Fail-loud was chosen to protect vector spaces, but it now poisons *planning* availability.
2. Is `recommend_skill` expected to be implemented (Phase 8B leftover), or should `execute_skill`'s contract be rewritten to accept raw store rows? Determines whether F2 is a missing feature or dead pipeline.
3. For LanceDB string columns holding JSON (metadata_json/steps_json/tags_json): do we want a repo-wide `_safe_json_loads(value, default)` util instead of per-site guards? Several sites already hand-roll slightly different variants.
4. `get_failure_penalty` is uncalled — keep hardening it (cheap), or flag for deletion in the dead-code sweep?
