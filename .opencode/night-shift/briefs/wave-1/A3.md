### F1 — 🟠 HIGH — `repl.py:464` (+463–513): background full-screen TUIs & interactive prompts race the main REPL for stdin

**File**: `libs/aja-core/aja/interface/repl.py`

Slash-command dispatch (`_handle_slash_command`) fire-and-forgets `_spawn_bg(asyncio.to_thread(...))` for `/kanban`, `/live`, `/missions` (`_open_dashboard`, line 464), `/tui` (`_open_curses_tui`, line 467), `/models` (`handle_models_command`, line 491 — uses rich `Prompt.ask`, see `cli/commands/models.py:57-81`), and `/schedule` (`_schedule_flow`, line 500 — `Prompt.ask`). The handler then returns `"handled"` and the main `run()` loop **immediately** calls `_read_input()` again (`asyncio.to_thread(session.prompt, ...)` at repl.py:275). Result: two OS threads concurrently reading stdin — one inside prompt_toolkit's raw-mode reader, one inside rich `Prompt.ask`/`input()` or a Textual/curses app.

**Repro sketch**: type `/schedule` with no args → REPL re-prompts while `_schedule_flow`'s `Prompt.ask("Enter objective...")` also waits on stdin → keystrokes are split nondeterministically between the two readers; with `/kanban`, typed characters vanish into the hidden prompt_toolkit buffer behind the alternate-screen board.

**Proposed fix**: make interactive slash commands *modal* — `await` them in the turn path instead of `_spawn_bg` (they already run via `to_thread`, so the loop stays responsive), or gate the main prompt behind an `threading.Event`/`asyncio.Lock` that bg interactive flows acquire before touching stdin.

### F2 — 🟠 HIGH — `dashboard.py:388-393`: sync LanceDB/scheduler providers called directly on the Textual event loop

**File**: `libs/aja-core/aja/tui/dashboard.py`

`refresh_sidebar()` (line 377) awaits `_safe_provider(fn)` where `data = fn()` invokes the provider **synchronously in the event-loop thread**, only checking afterwards whether the result happens to be a coroutine. The defaults (`_default_focus_refresh` → priority engine + AJAMemory; `_default_missions_refresh` → `memory.list_missions`; `_default_day_refresh` → `CronScheduler().list_jobs()`) all do LanceDB round-trips (~34 ms each per docs/operator/PERFORMANCE.md) plus first-call heavy imports. Fired by `set_interval(SIDEBAR_REFRESH_S=30)` and again at mount (on_mount line 350) — every refresh freezes all UI repaint/input for the duration; a cold cache can stall seconds (imports + embedding model paths).

Same pattern: `action_briefing_screen` (line 647: `text = self._briefing_fn()` → compose_briefing hits calendar + scheduler + memory synchronously) and `_ensure_core()` called inside `_run_turn` (line 518: gateway/registry construction on the loop).

**Repro sketch**: launch dashboard on a machine with slow disk; UI input lags exactly when the sidebar refreshes (every 30 s); pressing F3 during a slow briefing blocks the whole app.

**Proposed fix**: wrap each provider call in `asyncio.to_thread` inside `_safe_provider` (`data = await asyncio.to_thread(fn)`) — matches the Textual guidance that blocking work belongs in thread workers; same for `_briefing_fn` and `_ensure_core`.

### F3 — 🔴 CRITICAL — `tui.py:288`: blocking `subprocess.run(shell=True)` inside Textual async handler

**File**: `libs/aja-core/aja/interface/tui.py`

`AJAShell.audit_and_execute()` runs `subprocess.run(cmd, shell=True, capture_output=True, text=True)` with no timeout, called directly from the async `on_input_submitted` handler (line 268) — i.e., on the Textual event-loop thread. Any long-running command (`ping`, `npm install`, a hung process) hard-freezes the entire UI indefinitely; Ctrl+C is bound to quit so there's no interrupt path. Also `action_refresh_state` (line 198) calls sync `get_system_state()` (LanceDB reads) on the loop, and line 249 uses deprecated `asyncio.get_event_loop()` instead of `get_running_loop()`/`to_thread`.

**Repro sketch**: enter `ping localhost` in AJAShell input → whole TUI unresponsive until ping exits (never, if `-t` on Windows).

**Proposed fix**: replace with `proc = await asyncio.create_subprocess_shell(...)` + `await asyncio.wait_for(proc.communicate(), timeout=N)`, or offload to a Textual thread worker with `call_from_thread` for log updates. Replace `loop.run_in_executor(None, self.gateway.chat, ...)` with `await asyncio.to_thread(self.gateway.chat, ...)`.

### F4 — 🟡 MEDIUM — `curses_tui.py:379,389,392-394,402`: blocking MCP install/config-reload inside the Live render loop's async main

**File**: `libs/aja-core/aja/tui/curses_tui.py`

`handle_keypress('i')` → `install_selected_mcp()` executes `install_mcp_server(server_name)` (subprocess/network work), `load_and_validate_config()` (file IO), and appends logs — all synchronously inside `run_curses_tui_main`'s async loop (keypress drained at line 443-445). During install the whole dashboard (rich Live auto-refresh thread keeps drawing stale frames) stalls; a slow install also starves key processing. Similarly `render_control_panel` (line 324-325) calls `get_default_execution_manager().list_active()` on every frame (~10 fps) — repeated blocking IO per render tick wrapped only in a bare `except Exception`.

Also `AsyncKeyboardInput.__init__` (line 54) uses deprecated `asyncio.get_event_loop()` from constructor context; should capture `asyncio.get_running_loop()` in `run_curses_tui_main` and pass it in. And after `stop()`+loop close, the daemon reader thread's `call_soon_threadsafe` raises `RuntimeError: Event loop is closed` unhandled on the thread (line 79/116) — noisy stderr race at exit.

**Repro sketch**: press `i` on a server whose install takes >1 s → frozen frames, queued keys processed late; exit immediately after keypress → occasional "Event loop is closed" traceback from daemon thread.

**Proposed fix**: run installs via `await asyncio.to_thread(install_mcp_server, name)`; cache exec-state once per N frames; pass the running loop explicitly into `AsyncKeyboardInput`; wrap `call_soon_threadsafe` in try/except RuntimeError.

### F5 — 🟡 MEDIUM — `kanban.py:60-79,82`: LanceDB query executed inside `__rich__` on every Live frame

**File**: `libs/aja-core/aja/tui/kanban.py`

`KanbanBoard.get_column_data()` does `self.task_manager.manager.get_table(...).to_arrow()` + Arrow filters, and `__rich__` calls it — so at `refresh_per_second=10`, InteractiveKanbanApp's Live issues ~10 full LanceDB table reads per second, blocking the input-read loop between keys (input latency = query time). Failures are swallowed silently by bare `except Exception: pass` (line 77-78) — the board renders empty with zero diagnostics. Additionally the `a` add-task flow (lines 254-260) does `live.stop()` → `Prompt.ask` → `live.start()`: restarting a `screen=True` Live re-enters alt-buffer handling; combined with finding F1's stdin race this double-prompts.

**Proposed fix**: poll column data on a timer (e.g. every 0.5–1 s) outside `__rich__`, cache the result on the board object; log/dedupe the swallowed exception; reuse the paused-Live pattern only for genuinely modal prompts (and hold the REPL input gate).

### F6 — 🟡 MEDIUM — `repl.py:308-312` + `registry.py` interplay: fire-and-forget tasks swallow exceptions; REPL exit cancels mid-flight missions without notice

**File**: `libs/aja-core/aja/interface/repl.py`

`_spawn_bg` adds tasks to `_bg_tasks` with discard-on-done, but no done-callback retrieves exceptions — a failed `/swarm` mission (`_run_mission` catches broad Exception itself, OK) or any `to_thread` crash (e.g. `cmd_status` raising inside the worker thread) surfaces only as an orphaned "Task exception was never retrieved" warning, never rendered to the operator. Conversely, on `/exit` (`_cancel_bg_tasks`, line 305) long-running background missions are cancelled abruptly with no summary — acceptable, but combined with the silent-exception gap the user may believe a mission was launched when it died instantly. Note `to_thread` bodies **cannot be cancelled** (thread keeps running after `task.cancel()`) — `/exit` returns while a spawned doctor/status/models thread still holds stdin/LanceDB handles.

**Proposed fix**: add `task.add_done_callback(lambda t: t.exception() and self._console.print(f"[red]bg task failed: {t.exception()}[/red"))`; document/accept the uncancellable-thread caveat or use a cancellable design (asyncio subprocess).

### F7 — 🟡 MEDIUM — `conversation.py:405-473` (`_exec_chat`): event queue race window can drop/reorder final tool events; runner exception retrieval ordering

**File**: `libs/aja-core/aja/core/conversation.py`

The queue-drain loop creates `get_task = asyncio.create_task(queue.get())` per iteration; if the runner task completes simultaneously with a queued item, both are in `done`; they yield the item and `continue` — fine — but then next iteration's wait sees only `task`; `get_task.cancel(); await gather(...)` handles it. The subtle bug: after `break`, `await asyncio.gather(task, return_exceptions=True)` runs, then drains `queue.empty()` — events put by the runner *between* its last dispatch and gather completion ARE drained (good), but events put by `hooks.on_command` from a **different thread** (executor shell hooks may run threaded) would race `put_nowait` vs `empty()` check — currently all callers are same-loop, so latent only. Also line 481: `err is None and task.exception()` — safe because gather suppressed, but if `outcome["result"]` was set AND task raised afterwards (impossible in current runner shape), ordering is fragile. Severity low-medium; worth a comment/test rather than refactor.

Additionally `session["history"].extend(history[len(session["history"]) :])` (line 501) mutates shared history non-atomically across concurrent turns on the same chat_id — two parallel turns interleave history entries. InMemorySessionStore deep-copies per load/save, but `_working_history` aliases `history` list within one turn only; cross-turn concurrency is guarded only by the REPL's single-turn-at-a-time UX (dashboard enforces busy-lock, gateway adapters may not).

### F8 — ⚪ LOW — `terminal.py:26-117` + `curses_tui.py:51-127`: duplicated raw-mode keyboard readers with platform-divergent escape handling

**Files**: `libs/aja-core/aja/tui/terminal.py`, `libs/aja-core/aja/tui/curses_tui.py`

Two independent implementations of key decoding (msvcrt + select/tty). POSIX `read_key` toggles raw mode per call (tcgetattr/tcsetattr each poll — syscalls ×2 per 80 ms loop); POSIX path misses `left/right/delete` mappings present on Windows; neither decodes Home/End/PageUp. `read_key`'s KeyboardInterrupt raise inside kanban's Live context unwinds through `safe_fullscreen_console` correctly (finally restores buffer), but in `InteractiveKanbanApp.run` a Ctrl+C escapes as an exception to the caller rather than a clean `running=False` exit — inconsistent with 'q'. Race: between `kbhit()` and `getch()` another thread could consume the key (only relevant under F1's dual-reader conditions).

**Proposed fix**: consolidate on the curses_tui thread-reader (or a small shared module), extend POSIX arrow mapping, catch KeyboardInterrupt in kanban loop → graceful exit.

### F9 — ⚪ LOW — `intent_parser.py:451,531`: `print()` instead of logger; `parse_intent_async` fallback duplicates 80 lines of prompt text

Sync `parse_intent` performs a **blocking LLM `completion()` call** and is imported by chat surfaces — verify all call sites invoke it via `to_thread` (the REPL/gateway paths do; any new direct-await caller would block its loop). Error reporting uses `print(f"[IntentParser] Error ...")` which corrupts alternate-screen TUIs (Textual/curses) when triggered there. The two near-identical system prompts will drift (already diverged: tool list missing in async variant).

**Proposed fix**: logger + redact, extract shared prompt builder, keep async variant authoritative.

## Internet research

1. **Textual Workers Guide** — blocking requests in message handlers freeze UI; use `run_worker`/`@work(thread=True)`; thread workers must not touch UI directly, use `call_from_thread`; `exclusive=True` for stale-response races.
   https://textual.textualize.io/guide/workers/
2. **Textual App API — `call_from_thread`** — "Textual apps are not thread-safe… This method will ensure your code runs within the correct context"; raises RuntimeError if called from the app thread; `post_message` is the thread-safe alternative.
   https://textual.textualize.io/api/app/ · source: https://github.com/Textualize/textual/blob/main/src/textual/app.py
3. **DeepWiki: Textual Workers & Concurrency** — thread workers required for blocking/CPU ops; WorkerState lifecycle; Pilot.wait_for_idle testing implications.
   https://deepwiki.com/Textualize/textual/9.1-workers-and-concurrency
4. **Simon Willison — Anatomy of a Textual UI** — practical `@work(thread=True)` + `call_from_thread(update)` streaming pattern for sync LLM clients (directly applicable to F2/F3).
   https://simonwillison.net/2024/Sep/2/anatomy-of-a-textual-user-interface/
5. **prompt_toolkit 3.x asyncio docs** — must use `prompt_async()`/`Application.run_async()` inside asyncio apps; calling sync `prompt()` where a loop is running "will try to run the event loop again"; background tasks should use `app.create_background_task`.
   https://python-prompt-toolkit.readthedocs.io/en/master/pages/advanced_topics/asyncio.html
   https://python-prompt-toolkit.readthedocs.io/en/stable/pages/upgrading/3.0.html

   https://github.com/prompt-toolkit/python-prompt-toolkit/issues/1847
7. **Rich issue #1530 — Live/console not thread-safe** — printing to a Console with an active Live from other threads tears output/loses lines; Live has its own RLock but Console lock is separate; workaround discipline: only print via live.console or hold locks consistently.
   https://github.com/Textualize/rich/issues/1530
8. **Rich discussion #1401 — rich+asyncio** — structure Live ownership in one place; update from coroutines; relevant to repl.py's Live-per-stream design (single-threaded use here is compliant).
   https://github.com/Textualize/rich/discussions/1401
9. **Python asyncio dev docs** — blocking calls delay all tasks; `run_in_executor`/`to_thread` for blocking IO; loop APIs not thread-safe except `call_soon_threadsafe`/`run_coroutine_threadsafe`.
   https://docs.python.org/3/library/asyncio-dev.html

## Council questions

1. **F1 policy**: should interactive slash commands become modal (block the REPL until done — simplest, matches user mental model) or should the REPL grow a proper input-arbitration lock? Modal changes UX (no typing while kanban open — arguably desirable). Preference?
2. **C3 scope**: `interface/tui.py` (AJAShell) appears legacy/pre-ConversationCore (hardcoded gemini default, `<cmd>` prompting). Is it still a supported surface, or should we deprecate/delete it rather than invest in subprocess-hardening?
3. **C2 fix shape**: plain `asyncio.to_thread` wrappers vs adopting Textual's native `@work(thread=True)` + `call_from_thread` (better cancellation + error surfacing, bigger diff). Which does the council want as the house style for dashboard.py?
4. **ConversationCore concurrency contract** (F7): should `handle()` formally serialize per chat_id (asyncio.Lock keyed on chat_id) so gateway adapters can't interleave turns, instead of relying on surface-level busy gates?
5. **prompt_toolkit session threading** (related to F1): `session.prompt()` via `to_thread` may land on different worker threads across iterations; PromptSession isn't documented thread-safe across threads. Should we switch `_read_input` to a dedicated single input thread, or move to `prompt_async()` on the running loop entirely?
