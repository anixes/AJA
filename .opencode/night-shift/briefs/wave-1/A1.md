## Findings

### F1 — Sync LLM call blocks the gateway loop on every `/pc` command
- **File**: `gateway/remote_control.py:29` (via `interface/intent_parser.py:438`)
- **Severity**: CRITICAL
- **Description**: `async def execute_local_control` calls sync `parse_intent(...)`, which
  internally runs `completion(prompt=..., model=...)` — a synchronous LLM round-trip. The
  entire Telegram/Discord event loop freezes for the duration of the model call (seconds).
  An async twin (`parse_intent_async`, intent_parser.py:462) already exists and is unused here.
- **Repro**: send `/pc status` (or any `/pc …` that reaches the LLM layer) → all other chats'
  telemetry, approvals, and messages stall until the completion returns.
- **Fix**: `intent = await parse_intent_async(text, history, system_state=system_state)` or
  wrap in `asyncio.to_thread(parse_intent, ...)`.

### F2 — Synchronous tool execution (subprocess, up to 120 s) runs on the event loop
- **File**: `gateway/orchestrator.py:236-239` (chat tool loop) via `orchestration/tools/native.py:863`
  (`subprocess.run(cmd, shell=True, timeout=120)`) and `orchestration/tools/executor.py:45-53`
  (thread spawn + `thread.join()`)
- **Severity**: CRITICAL
- **Description**: In `UnifiedGateway.chat`, emitted native tool calls are executed with plain
  sync calls: `tool_registry.execute(fn_name, fn_args)` / `executor.execute(...)`.
  `NativeToolRegistry.execute` runs shell commands synchronously with a 120 s timeout;
  `ToolExecutor.execute` blocks the caller with `thread.join()` until a subprocess finishes.
  One chat turn running e.g. `git clone` freezes every other gateway chat, telemetry tail,
  approval button, and poller sharing that loop.
- **Repro**: two chats; chat A asks AJA to run a long shell tool via chat(); chat B's messages
  receive no response until A's subprocess exits.
- **Fix**: execute tools via `await asyncio.to_thread(tool_registry.execute, fn_name, fn_args)`
  (and same for executor), or use the async dispatch path already present in
  `ToolExecutor.dispatch_tool_calls`.

### F3 — Adapter-swap race: concurrent events clobber `orchestrator.telegram_adapter`
- **File**: `gateway/gateway_runner.py:93-99`
- **Severity**: HIGH (race condition)
- **Description**: `process_event` temporarily sets
  `self.orchestrator.telegram_adapter = AdapterProxy(adapter)` and restores the original in
  `finally`. Multiple adapter poll tasks (`_poll_adapter`) run concurrently on one loop; while
  a Discord event handler is mid-`handle_gateway_event` (a long await-heavy function), a
  Telegram event swaps it again. On restore, the "original" captured by whichever coroutine
  finishes first wins — replies and telemetry tails are then routed through the WRONG platform
  adapter (cross-posting user content to another platform = data-leak class bug).
- **Repro**: configure both TG+Discord tokens; send messages to both nearly simultaneously →
  intermittent wrong-platform replies.
- **Fix**: remove the mutation entirely — pass the adapter explicitly through
  `handle_gateway_event(event, responder=adapter)`; the MessageEvent already carries `platform`
  so routing can be deterministic.

### F4 — Blocking LanceDB session IO on the loop in telemetry tails (both platforms)
- **Files**: `gateway/tg_client.py:367,375`; `gateway/adapters/discord_adapter.py:532,550`
- **Severity**: HIGH
- **Description**: `tail_events` calls `gateway_state.get_session(chat_id)` and
  `update_session(chat_id, session)` synchronously inside `async def`. Both do real LanceDB IO
  (`open_table`, `search().where(...).to_list()`, `merge_insert(...).execute()`,
  see persistence.py:46-84). Every PLAN_CREATED/MISSION_*/NODE_* event performs multiple disk
  round-trips ON the event loop, once per tailed chat.
- **Repro**: run a mission emitting frequent NODE events with an active tail → visible
  `queue_lag_seconds` spikes and delayed message handling.
- **Fix**: wrap both calls in `await asyncio.to_thread(...)` (pattern already used elsewhere,
  e.g. orchestrator.py:449/487).

### F5 — Mission-hub LanceDB ops un-offloaded in `handle_gateway_event`
- **File**: `gateway/orchestrator.py:587,589-590,599,602,653,662,672-673` (+653 `create_task`)
- **Severity**: HIGH
- **Description**: `aja_memory.get_active_workers/create_mission/update_mission/list_missions/
  create_task` are synchronous LanceDB operations (`memory/secretary.py` is
  `lancedb.connect(DATA_DIR/'lancedb')` backed) called directly inside `async def
  handle_gateway_event` on MISSION/TASK_CAPTURE/STATUS intents. Phase-7 audit fixed heartbeats/
  sessions/scheduler off-loop but these hot-path mission calls were missed.
- **Repro**: `/status` right after a large journal write → UI-freeze proportional to table size.
- **Fix**: `await asyncio.to_thread(self.aja_memory.list_missions, status="PENDING")` etc., or
  add thin async wrappers on AJAMemory like approvals.py does (:59,:97,:116 — the correct pattern).

### F6 — Fire-and-forget Slack socket connect task: no reference, no error handling
- **File**: `gateway/adapters/slack_adapter.py:98`
- **Severity**: HIGH
- **Description**: `asyncio.create_task(self._socket_client.connect())` result is discarded.
  Per CPython docs, the loop holds only weak refs — the task may be garbage-collected
  mid-connect (aggravated in 3.12+ scheduling behavior), and if connect fails the exception is
  silently swallowed ("Task exception was never retrieved" at best). Slack then appears started
  (`is_running=True` set at :52) but never receives events.
- **Repro**: install slack_sdk, start with bad app_token → no traceback, adapter reports running.
- **Fix**: keep `self._connect_task = asyncio.create_task(...)` +
  `add_done_callback(_log_bot_task_done)` (the discord_envelope.py:63-69 helper shows the house
  pattern).

### F7 — Untracked fallback tail task in orchestrator
- **File**: `gateway/orchestrator.py:619`
- **Severity**: MEDIUM
- **Description**: For adapters without `start_tail`, `asyncio.create_task(
  self.telegram_adapter.tail_events(chat_id))` discards the Task (GC risk) and nothing ever
  cancels it on shutdown. The tracked `start_tail` path exists precisely because of this.
- **Fix**: store in a set with done-callback discard, or drop the fallback branch.

### F8 — Lost-update session race between event handler and telemetry tails
- **Files**: `gateway/orchestrator.py:449+482-487+706-713` vs `gateway/tg_client.py:367-375`
  (same shape in discord_adapter.py:532-550)
- **Severity**: MEDIUM (race condition / data integrity)
- **Description**: `merge_insert` makes each *row write* atomic, but both writers do
  read-modify-write of a whole-session JSON snapshot: `handle_gateway_event` fetches the session
  at :449, mutates it across a multi-second LLM turn, then writes the full snapshot at :713 —
  concurrently, `tail_events` fetched/mutated/wrote its own snapshot. Whichever writes last
  erases the other's history appends (user turns or system notes vanish from recall/history).
- **Repro**: trigger a mission (spawns tail system-notes) and immediately send follow-up chat
  messages → intermittently missing history entries afterwards.
- **Fix**: single-writer discipline — serialize per-chat session mutations through an
  `asyncio.Lock` keyed by chat_id (or move append-only updates into a dedicated queued writer).

### F9 — Unguarded PTB shutdown crashes `gateway.stop()` after failed startup
- **File**: `gateway/tg_client.py:162-165`
- **Severity**: MEDIUM
- **Description**: `stop()` unconditionally awaits `self._app.updater.stop()` /
  `app.stop()` / `app.shutdown()`. If the resilient-connect loop exhausted all 5 attempts
  before `start_polling` succeeded (or initialize itself failed), PTB raises RuntimeError
  ("not running"/updater not started) — the exception propagates out of `stop()`, skipping
  cleanup in `server.py` finally-block siblings and producing noisy shutdown crashes.
  (PTB v22 docs: updater.stop must precede app.stop — order here is correct, guarding is not.)
- **Repro**: invalid TELEGRAM_BOT_TOKEN ×5 retries → Ctrl-C during/after → AttributeError/
  RuntimeError instead of clean exit.
- **Fix**: guard each call (`if self._app.updater: try: await self._app.updater.stop()
  except Exception: logger.debug(...)`) mirroring telegram_envelope.py:124-132 which already
  wraps correctly.

### F10 — Cross-thread `asyncio.Queue.put_nowait` from bus handlers
- **Files**: `gateway/tg_client.py:255-311` (`_make_event_handler`/`_put_telemetry`);
  `gateway/adapters/discord_adapter.py:411-470`; publishers incl. `runtime/execution/manager.py:501`,
  `runtime/execution/sequencer.py:87`
- **Severity**: MEDIUM
- **Description**: Bus handlers are plain sync closures calling `telemetry_queue.put_nowait(ev)`
  on an `asyncio.Queue`. EventBus.publish is synchronous and invoked wherever events originate;
  several publisher paths run inside worker threads (e.g. execution manager emits from
  to_thread contexts / sequencer background work). `asyncio.Queue` is explicitly NOT
  thread-safe (no internal lock; waiter bookkeeping corrupts). Even without corruption today,
  a woken consumer may miss a put performed without `loop.call_soon_threadsafe`. The vestigial
  `loop = asyncio.get_event_loop()` capture at tg_client.py:256 (unused!) suggests this was
  originally intended to be thread-safe and regressed.
- **Fix**: capture the running loop in `_make_event_handler` and use
  `loop.call_soon_threadsafe(self._put_telemetry, ev)` when `threading.current_thread() is not
  loop-thread`; delete the unused `loop` variable otherwise.

### F11 — Sync status/diagnostics IO in local-control path
- **File**: `gateway/remote_control.py:86-105` (`_control_response`)
- **Severity**: MEDIUM
- **Description**: `status` → sync `list_missions×2 + get_active_workers` (LanceDB);
  `doctor` → `run_diagnostics()` (heavy probes incl. process/table checks) — all executed
  directly inside the async control flow.
- **Fix**: make callers `await asyncio.to_thread(_control_response, cmd)`.

### F12 — Minor hygiene cluster
- **Severity**: LOW
- Items:
  - `gateway/vision.py:33` — sync image cache write inside `async def describe_image`;
    wrap in to_thread (images can be MBs).
  - `gateway/tg_client.py:151-153` — `_tail_tasks` cancelled but never awaited in `stop()`
    (pending sends may still fire post-stop; also `stop_tails` clears queues while dispatcher
    may hold references).
  - `gateway/tg_client.py:256` — unused deprecated `asyncio.get_event_loop()` (see F10).
  - `gateway/daemon_manager.py:72` — `log_handle` opened, never closed (fd leak per boot);
    `start_daemon` (2× Popen) called synchronously from async `_auto_boot_local_worker`
    (orchestrator.py:770) — offload or make async.
  - `gateway/orchestrator.py:56,615-620` — `active_sub_agents` / `active_telemetry_bridges`
    mutated from concurrent event tasks without locks (benign today under GIL + single loop,
    breaks silently under any future multi-loop/threaded runner).

## Internet research

Verified against ACTUAL installed versions: python-telegram-bot **22.7**, httpx **0.28.1**,
Python 3.12.10 (discord/slack_sdk absent → simulated fallbacks active in this env).

1. **https://docs.python.org/3/library/asyncio-task.html#create_task** — Confirms: "Save a
   reference to the result of [create_task]... The event loop only keeps weak references to
   tasks. A task that isn't referenced elsewhere may get garbage collected at any time, even
   before it's done." Directly validates F6/F7 (set + `add_done_callback(discard)` pattern).
2. **https://mkennedy.codes/posts/fire-and-forget-or-never-with-python-s-asyncio/** —
   Documents that the GC race is aggravated in Python 3.12+ (this repo pins 3.12.10);
   exceptions in orphaned tasks surface only as "never retrieved" noise. Validates severity
   uplift of F6/F7 on this exact interpreter.
3. **https://docs.python-telegram-bot.org/en/v20.2/telegram.ext.application.html** (v22 docs
   equivalent text confirmed) — Canonical lifecycle order: `initialize → start →
   updater.start_polling → … → updater.stop → stop → shutdown`; also documents
   RuntimeError when stopping a non-started Application. Validates F9 (order used is correct;
   missing guards crash on failed startups).
4. **https://github.com/python-telegram-bot/python-telegram-bot** (README) — "Since v20.0,
   python-telegram-bot is built on top of asyncio... currently does not aim to be
   thread-safe." Supports keeping ALL PTB interaction on the single loop thread and treating
   cross-thread queue handoff carefully (F10).
5. **https://github.com/lancedb/lancedb/issues/3268** — Maintainers acknowledge the sync
   LanceDB API blocks event loops (AsyncTable.search wraps embedding calls in
   run_in_executor; add() does not). Confirms GatewayState/AJAMemory sync calls must be
   offloaded in async contexts (F4/F5/F11).
6. **https://tafreeman.github.io/agentic-runtime-platform/adr/ADR-035-rag-pipeline-architecture**
   — Independent production ADR adopting exactly this repo's correct pattern: sync LanceDB API
   wrapped per-call in `asyncio.to_thread`. Confirms the fix direction, not a rewrite.
7. **https://docs.slack.dev/tools/python-slack-sdk/socket-mode** + **https://github.com/slackapi/
   python-slack-sdk/issues/1922** + **issue #1913** — aiohttp-based SocketModeClient keeps ONE
   ClientSession for its lifetime and its `connect()` retry loop can spin forever against a
   closed session; abandoned connect tasks survive owner replacement. Validates F6 (task must
   be owned/referenced/cancellable) and adds context: even referenced, the client needs a
   watchdog since `is_connected()` misses dead-session state.
8. **httpx 0.28.1 semantics (local verify)** — `vision.py:48` uses `httpx.AsyncClient` per-call
   with timeout, correctly awaited; conforms to httpx async docs. No finding (per-call client
   creation is mildly wasteful but correct).
