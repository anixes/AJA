# A4 — Async/Event-Loop Audit Brief (Night-Shift Wave 1)

Scope: `aja/runtime/` (serve, autonomous_loop, single_instance, handover, lance_stores, events, event_bus), `aja/scheduler/cron_scheduler.py`, `aja/cognitive/` (temporal_graph, skill_compiler), `aja/goals/goal_engine.py`, `aja/autonomy/intent_engine.py`, `aja/presence/agent_loop.py`. READ-ONLY audit; no production code changed.

## Findings

### F1 — CRITICAL · `runtime/autonomous_loop.py:32-116` — external cancellation leaks zombie heartbeat task, intent engine, and worker.lock
`main_loop` has no `try/finally`. `serve.py:84` cancels the autonomy task on shutdown; `CancelledError` is a `BaseException` (3.8+), so neither the `except KeyboardInterrupt` nor `except Exception` handlers run:
- `heartbeat_task.cancel()` (autonomous_loop.py:81/103) never invoked → the 10s heartbeat loop keeps publishing ONLINE heartbeats from a leaked task (also never awaited after cancel → "Task was destroyed but it is pending" noise).
- `intent_engine.stop()` skipped → its asyncio task keeps running inside serve's loop.
- `release_lock(lock)` (line 116) skipped → stale `worker.lock`; next `aja serve` refuses to start ("Autonomous worker already running") until manual lock deletion.

Repro sketch: start `aja serve`, send SIGTERM (POSIX) or stop event, restart → duplicate-instance refusal + heartbeat rows still refreshing.
Proposed fix: wrap the `while True:` in `try/finally`; in `finally`: cancel heartbeat_task and `await asyncio.gather(heartbeat_task, return_exceptions=True)` if a loop is running, call `intent_engine.stop()`, `release_lock(lock)`.

### F2 — HIGH · `goals/goal_engine.py:406 → planning/planner.py:433 → llm.py:150-176` — planning LLM call freezes the entire shared event loop via thread-join
`_step_planning` (async) calls sync `expand_goal()` → `planner.decompose()` → `run_async_synchronously(gw.complete(...))`. When a loop is already running (always true under `serve`), that helper spawns **a fresh thread with a new event loop per call** and blocks the caller with `t.join()` (llm.py:175) for the full LLM round-trip (seconds–minutes). During that window: heartbeats stall, cron tick_loop stalls (missed minute boundaries), gateway adapters stall. Also unbounded thread creation and no timeout on `res_future.result()`.
Repro sketch: schedule any goal; observe cron ticks / heartbeat gaps aligning with PLAN_CREATED latency.
Proposed fix: make `_step_planning` use `await asyncio.to_thread(self.expand_goal, goal)` as an immediate remediation (planner stays sync); longer term add an async decompose path so `run_async_synchronously` isn't invoked on-loop at all.

### F3 — HIGH · `scheduler/cron_scheduler.py:684,712,720,766` + `runtime/events.py:116` — every scheduler tick does blocking LanceDB IO on the event loop
`tick_loop` runs every 1s and calls `self.store.list_tasks(status="scheduled", limit=10000)` plus `store.update_task(...)` synchronously; each job lifecycle also calls `_emit_event` → `LanceRuntimeEventSink.emit` → `memory.add_runtime_event` (LanceDB write). Under `serve` this shares one loop with gateway + autonomy. LanceDB opens/writes are disk-bound ms-to-tens-of-ms stalls each second, worst-case worse on cold cache or AV scans.
Related: `_execute_briefing_job` (cron_scheduler.py:582) calls `send_briefing()` synchronously — calendar reads + bi-temporal graph queries block the loop for the whole briefing composition.
Repro sketch: profile tick_loop with several jobs; measure event-loop lag (`loop.slow_callback_duration`).
Proposed fix: offload store/sink calls with `asyncio.to_thread` (or introduce async methods on `RuntimeTaskStore`/`RuntimeEventSink` protocols); wrap briefing compose in to_thread.

### F4 — MEDIUM · `scheduler/cron_scheduler.py:566` — blocking `time.sleep(0.05)` retry inside async context
`_mutate_job_meta` sleeps synchronously between write retries; called from the async `_execute_job` `finally` (line 535) and reminder paths → blocks the loop 50ms per failed attempt (and it's a read-modify-write race band, not just latency).
Proposed fix: drop the sleep (retry immediately once) or convert to an async method using `await asyncio.sleep`.

### F5 — MEDIUM · `runtime/serve.py:28-70` — Windows signal path: SIGTERM effectively undeliverable; Event.set from signal handler
Fallback `signal.signal(sig, lambda *_: _handle())` calls `stop_event.set()` directly. It works only because Python signal handlers always execute in the main thread (docs), but the canonical pattern is `loop.call_soon_threadsafe(stop_event.set)` — safer if handlers are ever installed from another thread, and it avoids waking waiters mid-callback. Bigger issue: on Windows, external SIGTERM delivery doesn't exist (only SIGINT/SIGTERM/SIGBREAK set is signalable in-process); docker `stop` on Windows containers won't reach this handler, so graceful teardown there relies on KeyboardInterrupt/stop-event plumbing only. The NotImplementedError catch for `add_signal_handler` matches documented ProactorEventLoop limitations — that part is correct.
Repro sketch: on win32, `os.kill(pid, signal.SIGTERM)` from another process → no handler invocation (no-op/strong-exit semantics).
Proposed fix: use `loop.call_soon_threadsafe`; document that Windows deployments need the stop-event/healthcheck path (e.g., optional local "shutdown" control channel) rather than signals.

### F6 — MEDIUM · `autonomy/intent_engine.py:216,131,139,161` + `scheduler/telegram.py:84` — autonomous intents do blocking LanceDB/file IO on the loop
`IntentEngine.loop` (asyncio task created by `start()`, not a thread despite the comment at autonomous_loop.py:59) invokes sync `execute()`: `goal_engine.add_goal` → LanceDB mission write; `experience_store.save`; `save_cooldowns` file write; and `_send_telegram_report` constructs a **fresh `LanceRuntimeEventSink()` per call** (new LanceDB store open) — repeated blocking IO inside the autonomy cycle. Unsafe-intent escalation path hits the same sink construction.
Proposed fix: hoist a single shared event sink; route store writes through to_thread; fix the misleading "background thread" comments.

### F7 — MEDIUM · `cognitive/skill_compiler.py:75,212-249` — sandbox dry-run subprocess blocks the calling loop up to 15s
`distill_trajectory` runs `_sandbox_dry_run` with `subprocess.run(timeout=15)` synchronously. It is invoked by the orchestrator during missions executing on the event loop → up to a 15s full-loop freeze per compiled skill.
Repro sketch: compile a skill mid-mission while gateway chat is active; observe request latency spike ≈ dry-run duration.
Proposed fix: `await asyncio.to_thread(compiler.distill_trajectory, trajectory)` at the orchestrator call site.

### F8 — LOW/MEDIUM · `runtime/serve.py:86-93` + `cron_scheduler.py:795-805` — startup projection rebuild blocks the live loop
`scheduler.start()` runs `rebuild_scheduler_projections()` (full journal replay, LanceDB-heavy) synchronously before spawning tick_loop; `serve()` calls it after the loop is already serving. One-time but can delay gateway readiness by seconds.
Proposed fix: rebuild in a thread and await it before starting the tick task (or move before `run_gateway()`).

### F9 — LOW · `presence/agent_loop.py:143-144` — `signal.signal` unguarded against non-main-thread start
`signal.signal(SIGINT/SIGTERM, ...)` raises `ValueError` when called off the main thread (docs). If `run_loop` is ever hosted in a worker thread (likely given the thread-style design), startup crashes.
Proposed fix: try/except ValueError around registration; rely on the existing `stop_loop` flag file for threaded mode.

### F10 — LOW · `runtime/event_bus.py:54-69` — sync publish drops awaitable results of async handlers
During scheduler-driven publishes (`_fire_reminder`, report delivery) async subscriber coroutines get `.close()`d and warned instead of scheduled — silent non-delivery whenever a platform adapter registered an async telemetry tail handler and someone publishes from a sync path.
Proposed fix: schedule stray awaitables with `asyncio.get_running_loop().create_task(result)` when a loop exists (keep `.close()` fallback otherwise).

### F11 — INFO (verified OK, with caveat) · `cognitive/temporal_graph.py:88-103`
Per-operation connections (`_transaction` opens/closes a fresh `sqlite3.connect`) mean **no cross-thread connection reuse** and no `check_same_thread` hazard; WAL + unique partial index look correct. Caveat: all graph ops remain synchronous, and `timeout=10.0` means a caller invoking graph methods directly on the event loop (briefing composer, calendar sync, recall) can stall the loop up to 10s under writer contention. Callers should wrap in to_thread (recall.py already partially does). No busy_timeout pragma alignment beyond connect timeout; consider explicit `PRAGMA busy_timeout` + `synchronous=NORMAL` per hardened-baseline practice.

## Internet research

- Python docs — Platform Support: `loop.add_signal_handler()` / `remove_signal_handler()` are **not supported on any Windows event loop** (Proactor default since 3.8); Proactor limitations enumerated. https://docs.python.org/3/library/asyncio-platforms.html
- Python docs — signal: handlers always executed in the main thread; only main thread may install handlers (`ValueError` otherwise); on Windows `signal()` accepts only SIGABRT/SIGFPE/SIGILL/SIGINT/SIGSEGV/SIGTERM/SIGBREAK. https://docs.python.org/3/library/signal.html
- CPython bpo-44592/issue78860 — `add_signal_handler` fails off-main-thread; ProactorEventLoop `set_wakeup_fd` main-thread restriction history. https://github.com/python/cpython/issues/78860
- StackOverflow — Windows `add_signal_handler` raises NotImplementedError; Windows lacks real IPC signals ("signals on Windows" MSDN context). https://stackoverflow.com/questions/58014623/python-asyncio-notimplementederror
- sqlite3 docs — `check_same_thread` semantics; `timeout` = lock-wait seconds; threadsafety levels (module-share vs connection-share). https://docs.python.org/3/library/sqlite3.html
- SQLite official — threading modes (multi-thread: no connection shared across threads simultaneously); WAL concurrency: readers don't block writer, single writer, checkpoint starvation. https://www.sqlite.org/threadsafe.html , https://sqlite.org/wal.html
- SQLite hardening guides — connection-scoped PRAGMAs (`busy_timeout` ms vs connect `timeout` s), single-writer routing, WAL checkpoint tuning. https://www.productionhardening.org/wal-optimization-concurrency-tuning/connection-pooling-strategies/ , https://www.productionhardening.org/sqlite-architecture-production-hardening/busy-timeout-configuration/
- APScheduler — misfire_grace_time/coalesce/max_instances patterns; persistent stores require static ids + conflict policy; async executors must not run blocking jobs on the loop (maintainer: "use other executors for those blocking operations"). https://apscheduler.readthedocs.io/en/master/userguide.html , https://github.com/agronholm/apscheduler/discussions/999

## Proposed claims

1. **A4-claim-autoloop-finally**: Add cancellation-safe `try/finally` cleanup to `main_loop` (F1) + regression test simulating external cancel asserting lock release & heartbeat task done.
2. **A4-claim-scheduler-offload**: Offload `tick_loop` store IO, `_emit_event` sink, `_mutate_job_meta` sleep, briefing compose, and startup projection rebuild to threads / async store ports (F3, F4, F6, F8).
3. **A4-claim-planner-offload**: `to_thread` the sync planner path in `_step_planning` (F2) and skill-compiler dry-run call site (F7).
4. (Optional, needs council input) F5/F10 behavior changes touch cross-platform semantics — see questions.

## Council questions

1. Should we evolve `RuntimeTaskStore`/`RuntimeEventSink` protocols with native `async` methods (bigger refactor, cleaner contract) rather than sprinkling `to_thread`? Who owns the protocol files?
2. `run_async_synchronously` (llm.py) is used in multiple sync paths (planner, GoogleModelProvider). Do we deprecate it repo-wide in favor of structured async, or keep it but ban calls from running loops (debug-mode assertion)?
3. For Windows `aja serve` (VPS kit targets Linux, but dev hosts are Windows): is a stop-event side channel acceptable, or do we accept Ctrl+C-only graceful shutdown and document it?
4. EventBus sync-publish dropping awaitables (F10): silently scheduling tasks changes failure semantics (unobserved task exceptions). Prefer strict warning + adapter-side fix, or auto-scheduling?
