# G2 Brief — Approval Pipeline Bug Hunt (Gateway/Surfaces)

Agent: G2 (Gateway/Surfaces subgroup) · Wave 2 · READ-ONLY research
Scope: `gateway/approvals.py`, approval callbacks in `tg_client.py` / `adapters/discord_adapter.py` / `adapters/slack_adapter.py` (+ envelope adapters), orchestrator/`goal_engine` approval emission, `api/bridge.py` approval routes, mission approval expiry/idempotency, `messaging/envelope.py` widget round-trip.
Excludes Wave 1 findings (NULL-status telemetry, session validation) — not re-reported.

---

## Findings

### F1 - CRITICAL - `ConversationCore.resolve_approval` calls the shared engine with a mismatched signature: wrong mission resolved, reject impossible
- Files: `core/conversation.py:598-602`; callers `interface/repl.py:665`, `tui/dashboard.py:215`; engine contract `gateway/approvals.py:42-47`
- Code:
  ```python
  # conversation.py
  async def resolve_approval(self, approval_id: str, approved: bool, approver_id: str = "") -> dict:
      from aja.gateway.approvals import resolve_approval
      return await _maybe_await(resolve_approval(approval_id, approved, approver_id))
  ```
  The shared engine signature is `resolve_approval(platform, user_id, mission_id, action="approve")`. Positional mapping is therefore:
  - `platform = approval_id` (e.g. `"approval-1756..."`) — logging only
  - `user_id = approved` — a **bool** logged as the acting user
  - `mission_id = approver_id` — **the approver's user id string becomes the mission lookup key**
  - `action` stays default `"approve"` — the `approved` flag is consumed as `user_id`, so **reject is unreachable**
- Live paths: REPL approval events (`repl.py:665`, passes `approver_id=self._user_id`) and TUI dashboard (`dashboard.py:215`, passes no approver → `mission_id=""`). Both resolve `get_mission(<user-id or "">)` → None → user sees "no longer exists or was already handled" for every legitimate CLI/TUI approval. If a mission id ever collided with an approver id, it would be force-approved regardless of the operator's choice.
- Class: signature-drift across a refactored seam (the Phase 7 "shared approval engine" extraction changed parameter order/semantics without updating this caller).
- Proposed guard: `resolve_approval(platform="cli", user_id=approver_id, mission_id=approval_id, action="approve" if approved else "reject")` — plus decide whether REPL/TUI approvals are *mission* approvals or *tool-command* approvals (`aja_approvals` table via bridge); today they are wired to neither correctly.

### F2 - HIGH - Naive `expires_at` crashes `resolve_approval` with uncaught TypeError; buttons stay live
- File: `gateway/approvals.py:74-87`
- Code: `parsed = datetime.fromisoformat(str(expires_at).replace("Z", "+00:00"))` then `datetime.now(timezone.utc) > parsed`. If metadata carries an offset-less ISO stamp (`"2026-08-25T12:00:00"`, plausible from hand-edited state, older writers, or cross-version data), `parsed` is naive. Per Python docs, ordering comparison between naive and aware raises `TypeError` ([docs.python.org/3/library/datetime.html](https://docs.python.org/3/library/datetime.html): "Order comparison between naive and aware datetime objects raises TypeError"). The handler catches only `ValueError` → TypeError escapes.
- Blast radius: every adapter callback path calls `resolve_approval` with **no local try** (`tg_client.py:536`, `discord_adapter.py:301`, `discord_envelope.py:219`). Exception hits the platform handler; the message keeps its pending keyboard and the user gets zero feedback — a permanently clickable phantom button that errors on every press.
- Contrast: `bridge.approval_is_expired` (bridge.py:1067-1077) wraps in bare `except Exception → return True` (fail-closed). The mission-side engine should match.
- Proposed guard: catch `(ValueError, TypeError)`; on parse failure treat as expired (or at minimum fail-closed with a user-visible message).

### F3 - HIGH - Double-approve/double-reject race: check-then-act idempotency with no atomic claim
- Files: `gateway/approvals.py:59-129`; store layer `memory/secretary.py:457-496`
- Trace: `resolve_approval` reads mission status via `get_mission` (LanceDB search), checks `_TERMINAL_OR_ACTIVE_STATUSES` (approvals.py:89), then writes `update_mission(status=...)` which is itself another read + journal emit (`secretary.py:457-466`). There is no compare-and-swap: two concurrent callbacks (double-click before the first edit lands; Telegram retry redelivery + Discord click on a mirrored/forwarded keyboard; both adapters tailing the same LanceDB AWAITING_APPROVAL row) both observe `AWAITING_APPROVAL`, both pass the guard, both emit `NODE_APPROVED`/`NODE_REJECTED` and both report success. Same TOCTOU shape exists on the tool-command side: `approve_runtime_approval` (bridge.py:1080-1171) re-checks `status == "pending"` at :1062 then executes the shell command and only afterwards flips status (:1144) — two concurrent HTTP `/telegram/command approve` calls **execute the guarded command twice**.
- Aggravator: `update_approval`/`update_mission` return values / affected-row counts are never checked, so a lost update is invisible.
- Proposed guard: claim-first transition — update status to a terminal value *before* side effects and verify exactly 1 row updated (LanceDB `table.update` result), or gate on a single-flight asyncio lock keyed by mission/approval id per process.

### F4 - MEDIUM - Mission approval expiry enforcement is dead code: nothing ever writes `approval_expires_at`
- Files: `gateway/approvals.py:73` (reader); repo-wide grep shows zero writers of `approval_expires_at` into mission `metadata_json` (`goal_engine.escalate_to_user` writes only `{message, mission_id}` payload, goal_engine.py:244-252; `create_mission` emits empty `metadata: {}`, secretary.py:443-447).
- Consequence: mission approval keyboards never expire — an AWAITING_APPROVAL button from last week still transitions the mission to ACTIVE if its status hasn't moved. Only the separate `aja_approvals` table path (bridge, `expiresAt` at bridge.py:938-960) has real expiry. The docstring promise at approvals.py:8 ("Approval expiry enforcement") is unfulfilled for missions.
- Related: `escalate_to_user` defaults to `mission_id="system"` (goal_engine.py:244), producing buttons `approve_system`/`reject_system` (tg_client.py:386-387) that always dead-end in "Mission system no longer exists". Also `react_executor.py:161,225` publishes AWAITING_APPROVAL with graph/node payloads lacking `mission_id` entirely → adapters render buttons targeting `"system"`.
- Proposed guard: write `approval_expires_at` when entering AWAITING_APPROVAL; refuse to render approval keyboards when target has no resolvable mission.

### F5 - MEDIUM - Envelope Telegram truncation slices characters, not bytes, and silently corrupts action ids
- File: `adapters/telegram_envelope.py:166` — `callback_data = _callback_data_from_action_id(widget.action_id)[:64]`
- Telegram's limit is **1-64 UTF-8 bytes**; exceeding it rejects the entire message with `Bad Request: BUTTON_DATA_INVALID` ([core.telegram.org/bots/api](https://core.telegram.org/bots/api) InlineKeyboardButton; [conferbot.com/errors/telegram/400-bad-request-button-data-invalid](https://www.conferbot.com/errors/telegram/400-bad-request-button-data-invalid) — "The limit is in bytes... 64 characters of non-ASCII text can be far more than 64 bytes"). Python `[:64]` counts **characters**, so a non-ASCII widget id passes this guard and still fails at send time (send_message swallows it → approval request never delivered, no error surfaced beyond metrics).
- Additionally, silent truncation can split mid-id: `approve_M-AB1…` → callback resolves a *different* (prefix-colliding) or nonexistent mission instead of failing loudly. Round-trip partner `_action_id_from_callback_data` (telegram_envelope.py:52-55) also matches `startswith(("approve", "reject"))` without separator, so any future widget whose label begins "approve…" is misrouted into the perm namespace.
- Note: envelope adapters (`TelegramEnvelopeAdapter`/`DiscordEnvelopeAdapter`) have no production instantiation yet (grep: definitions only) — latent, but they are declared the migration replacement for tg_client.py.
- Proposed guard: `len(cb.encode("utf-8")) <= 64` validation with loud failure; opaque short keys instead of embedding ids.
- Discord contrast: `custom_id` max is 100 **characters** and discord.py does not truncate ([discord docs — Message Components](https://github.com/discord/discord-api-docs/blob/main/docs/interactions/Message_Components.md): "max 100 characters"); current prefixes `aja:approve:` (12) + `M-XXXXXX` fit comfortably, but nothing validates.

### F6 - LOW - DiscordEnvelope success/failure edit leaves buttons attached (phantom pending controls)
- File: `adapters/discord_envelope.py:222` — `await interaction.response.edit_message(content=text)` with **no `view=None`**.
- After ANY resolution (approved, rejected, expired, already-handled) the inline buttons remain attached and clickable. Every subsequent click round-trips `resolve_approval` again (safe-ish due to status guard, but noisy journal reads, and pre-F3-fix it was a genuine double-apply window). Compare sibling `adapters/discord_adapter.py:320,352` which correctly pass `view=None`.
- Proposed guard: add `view=None` to the edit (and consider disabling rather than removing on failure paths for auditability).

### F7 - LOW - Slack has no approval surface but receives approval telemetry as plain text
- File: `adapters/slack_adapter.py:141-155` (`tail_events` renders `[STATUS] message` for all kinds; no AWAITING_APPROVAL branch, no interactive payload).
- An operator following a mission from Slack sees "⚠️ APPROVAL REQUIRED: …" text (via generic path) with no way to act — stranded-approval UX, not a security hole (auth is enforced elsewhere). Wave-1 F2 fixed Slack's missing tail *methods*; this is the remaining semantic gap: tails deliver intents Slack cannot fulfill.
- Proposed guard: feature-flag approval kinds per adapter capability, or append "approve via Telegram/CLI: `approve <id>`" hint text.

### F8 - LOW - `/runtime/deny` ignores rejection result before notifying the user
- File: `api/bridge.py:2391-2398` — Telegram branch assigns `result = reject_runtime_approval(...)` then unconditionally messages "Dashboard rejected …" and returns `result`; unlike the approve branch (:2373-2375) there is no `result["ok"]` check/HTTPException. A failed reject (unknown id, ownership mismatch) still tells the chat it was rejected.
- Proposed guard: mirror the approve branch's ok-check.

### F9 - INFO - Auth coverage asymmetry across callback surfaces (verified OK where implemented, absent where not)
- tg_client.py:522-532: user-checked against `TELEGRAM_ALLOWED_USER_ID` (config-fallback), fail-closed on empty/`*`. Does NOT check `query.message.chat_id` — acceptable since authorization is user-scoped, but note a forwarded approval message lets the allowed user act from any chat (by design?).
- telegram_envelope.py:319 + discord paths: route through `is_user_authorized(platform, user_id)` — consistent.
- slack: no callback surface at all (F7).
- `int(telegram_user) != int(user_id)` at bridge.py:1090/1181 raises ValueError for non-numeric ids (uncaught in deny path) — cosmetic hardening item.

## Proposed claims

1. C1: Shared-engine extractions must be call-site-audited for positional-argument drift; `resolve_approval(platform, user_id, mission_id, action)` is semantically incompatible with `(id, bool, str)` and Python cannot catch it. (F1)
2. C2: Expiry parsing must be total: unknown/malformed expiry ⇒ fail-closed (expired), matching bridge behavior; never let TypeError escape into platform handlers. (F2)
3. C3: Approval state transitions need claim-before-effect semantics (atomic status flip verified by affected-row count) before executing commands or emitting journal rows. (F3)
4. C4: Platform byte limits must be enforced in UTF-8 bytes at keyboard-build time with loud failure, never by silent character-slice truncation of action ids. (F5)
5. C5: Post-resolution UI must remove/disable buttons in the same interaction response that reports the outcome. (F6)

## Council questions

1. F1: Are REPL/TUI approvals meant to target *missions* (`aja_missions`) or *tool commands* (`aja_approvals`)? Today the wiring satisfies neither; who owns deciding the contract?
2. F3: Is a per-process asyncio lock sufficient, or do we need LanceDB-level CAS (`table.update` returning count) given multi-process `aja serve` + workers share DATA_DIR?
3. F4: Should AWAITING_APPROVAL without a resolvable mission be dropped at the adapter (no keyboard) or rendered disabled-with-explanation?
4. F5: Since envelope adapters are uninstantiated, fix now cheaply or gate behind the migration milestone with a unit test asserting byte-budget for the largest real widget set?
5. F9: Should Telegram callback auth additionally pin `query.message.chat_id` to the chat that received the original approval, to neutralize forwarded-button actions?
