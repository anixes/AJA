Scope: `aja/orchestration/tools/native.py`, `tools/executor.py`, `aja/llm_structured.py`,
provider adapters' tool translation, MCP schema registration (`aja/api/mcp_client.py`,
`aja/mcp/mcp_client_manager.py`).

Note: `briefs/wave-1/T2.md` does not exist anywhere in the repo (no `briefs/` dir at all).
The str/dict tool-argument duality was therefore not re-audited per instruction; argument

Internet mandate satisfied - citations inline (OpenAI function-calling / structured-outputs

## F1 [HIGH] Non-object-root schemas sent as synthetic-tool parameters -> provider 400 on strict OpenAI-compatible endpoints

`llm_structured._emit_result_tool()` (llm_structured.py:141-155) uses the caller's schema
verbatim as `function.parameters`. Swarm planning passes an array-root schema
(`PLAN_SCHEMA = {"type": "array", ...}` swarm.py:250-257; simplified rung-2 schema
swarm.py:363-370 is also array-root). The OpenAI Chat Completions family requires function
`parameters` to be an object schema; array roots trigger
`400 Invalid schema for function ... Input must be an "object" or "boolean" type`.
Citations:
- https://portkey.ai/error-library/schema-validation-error-10059 ("Input must be an object or boolean type")
- https://community.openai.com/t/api-rejects-valid-json-schema/906163 ("schema must be a JSON Schema of 'type: object'")
- https://developers.openai.com/api/docs/guides/structured-outputs ("the root level object of a schema must be an object")

Compounding it: `openai_compat.chat()` classifies 400 as NON-RETRYABLE and returns an EMPTY
`LLMResponse(content="")` (openai_compat.py:51, 245-251). That empty response flows into
`_extract_and_validate` -> no parsable JSON -> `StructuredOutputError` -> recovery ladder rung 1
and rung 2 both reuse array-root schemas -> ladder always exhausts -> silent degrade to
single-step plan (swarm.py:283-284). Net effect: on strict providers, HTN multi-subtask
planning silently never happens. Additionally, even where a model accepts the call,
tool-call arguments are protocol-mandated JSON objects, so a top-level-array contract is
structurally awkward for Strategy A regardless of provider leniency.

Fix direction: wrap array roots as
`{"type":"object","properties":{"items": <root>},"required":["items"]}` inside
`_emit_result_tool` and unwrap after validation.

## F2 [HIGH] Advertised tool names contain dots -> guaranteed 400 from name-validating providers

Native schemas advertise `browser.extract_markdown`, `browser.wait_for_selector`, ... ,
`desktop.*` (native.py:444-635) and MCP tools register as `mcp.{server_id}.{name}`
(api/mcp_client.py:14-16) - all containing `.`. OpenAI/Azure/DeepSeek validate
`^[a-zA-Z0-9_-]{1,64}$`; Anthropic `^[a-zA-Z0-9_-]{1,128}$`; Gemini forbids periods too.
All three AJA adapters pass names through raw: openai_compat sends whole tools untouched
(openai_compat.py:198-199), anthropic `_translate_tools` copies `fn["name"]` verbatim
(anthropic_adapter.py:63-76), google `_convert_tools` same (google_adapter.py:131-142).
Evidence:
- https://github.com/OpenCoworkAI/open-cowork/issues/159 (DeepSeek 400: "Invalid 'tools.function.name': string does not match pattern '^[a-zA-Z0-9_-]+$'" for MCP dot/colon names)
- https://github.com/lukilabs/craft-agents-oss/issues/498 (Anthropic 400 for dotted MCP tool names)
- https://community.openai.com/t/clarifying-tool-name-rules-for-mcp-and-openai-apis/1365988 (MCP allows dots, OpenAI does not; 64-char cap)
- https://portkey.ai/error-library/input-validation-error-10046 (pattern + 64-char limit)

Also unbounded length risk: `mcp.{long_server}.{long_tool}` can exceed 64 chars.
Fix direction: sanitize to `[a-zA-Z0-9_-]` at the adapter boundary with a reverse map
(original name kept in non-API metadata keys).

## F3 [HIGH] Signature drift misclassified as SUCCESS in ActivityRuntime python path

`registry.execute()` catches any exception and returns the string
`"Tool Execution Error: {e}\n{traceback}"` (native.py:680-686) - including TypeErrors from
schema/signature drift (LLM emits wrong kwarg names vs `self.tools[name](**arguments)`).
`ActivityRuntime._run_python` classifies failure via
`result_str.startswith("Error") or startswith("Security Error")` (activity_rt.py:290-297).
"Tool Execution Error:" starts with "Tool" -> `success=True`, `error=None`, `data=None`.
A mid-mission TypeError therefore journals `TOOL_COMPLETED(success=True)` with no payload -
exactly the "silent TypeError mid-mission" class this hunt targeted. Secondary: any legit
tool output whose first line begins with "Error" is misclassified as failure.

Fix direction: have `execute()` return structured results or use a distinct sentinel prefix;
check `"Tool Execution Error"` explicitly.

## F4 [MEDIUM] Gateway chat loop routes non-native advertised tools into ToolExecutor as shell commands

`gateway/orchestrator.py:236-239`:
`if fn_name in tool_registry.tools: registry.execute(...) else: executor.execute(fn_name, fn_args)`.
`browser.*`, `desktop.*`, `mcp.*` are advertised in `get_schemas()` but NOT in
`self.tools` (register_default_tools native.py:42-65 has none of them), so they fall into
`ToolExecutor.execute(command, cwd=None)` (executor.py:144) where the tool name becomes a
shell command string and the args dict is bound to `cwd`. Result: classify_command("browser.click"),
a doomed subprocess spawn with `cwd=<dict>`, and a confusing error fed back to the model -
instead of routing through ActivityRuntime's `_run_browser/_run_desktop/_run_mcp`
(activity_rt.py:147-152), which handle these correctly. Direct-loop path is fine
(dispatch_tool_calls -> registry.dispatch -> ActivityRuntime, executor.py:165-186).

## F5 [MEDIUM] Malformed arguments JSON silently coerced to empty dict, no repair fallback

Both LLM->tool argument parse sites do bare `json.loads` then `except Exception: args = {}`
with NO single-quote / trailing-comma / fence-stripping fallback:
- gateway/orchestrator.py:225-229 (`fn_args = {}`)
- orchestration/direct_loop.py:186-190 (`t_args = {}`)
Consequence: required params go missing -> registry returns "Tool Execution Error:
... missing 1 required positional argument" (which per F3 is then journaled as SUCCESS).
The model also never learns its JSON was malformed; it receives an unrelated-looking error.
`extract_json_object()` (llm_structured.py:120-138) already implements the tolerant
extraction needed - it is just not reused here. Note: T2 reportedly verified str/dict
duality end-to-end; this finding is about the no-fallback failure mode of that parse, not
the duality itself.

## F6 [LOW-MED] Registry name-collision and global-state hazards

- `NativeToolRegistry._external_schemas` is a CLASS-level mutable dict shared by every
  instance across missions (native.py:15). `register_external_schema` silently overwrites
  on duplicate name (no warning), and `clear_external_schemas` exists but instances never
  clear; two servers registering colliding names (or an external schema named e.g.
  `read_file`) silently shadow. Also `get_schemas()` can then return duplicate tool names
  (default + external) in one list.
- `dispatch()` calls `get_schemas()` on EVERY dispatch (native.py:702); get_schemas()
  re-imports and re-registers MCP schemas each call (native.py:672-677) under a bare
  `except Exception: pass`. Wasteful and side-effectful on the hot dispatch path.
- No validation against provider constraints (charset/64-cap) at registration time.

## F7 [LOW] structured_completion edge cases

- Repair loop itself is bounded (`max_repair`, default 1) - no infinite case found.
  However if the response contains no raws at all, `last_raw` stays None and the repair
  prompt embeds literal "None" as the previous response (llm_structured.py:222-229) -
  wasted round-trip with degraded signal.
- `validate_against_schema` ignores enum/const/min/max/format; unknown entries in a type
  list are silently dropped (empty checker list skips the check entirely,
  llm_structured.py:66-74). Output contracts relying on enums are unenforced.
- `one_round` always passes `model=model` even when None (llm_structured.py:207);
  `gateway.chat(model, ...)` treats model positionally-required - None flows to adapters
  and produces provider errors rather than default-model resolution (gateway only defaults
  copilot models). Minor.
- PLAN_SCHEMA uses `"id": {}` (swarm.py:254) - empty schema means "any type"; tolerated in
  non-strict mode but rejected by strict-mode providers and meaningless to the validator.

## Verified-clean areas (no action)

- All native schema param sets match their execute() signatures exactly (checked all 22
  python tools incl. optionals git_diff(path=None), delete_path(recursive=False),
  query_past_experiences(limit=3), search_web/fetch_url/max_chars, get_datetime(location)).
- Anthropic/Google adapters correctly strip AJA-custom keys (`activity_type`,
  `retry_policy`, `required_scope`, `metadata`) before sending; only openai_compat forwards
  them raw inside `function` (tolerated by OpenAI today, but unvalidated on smaller
  OpenAI-compatible backends - fold into F2's adapter-boundary sanitization).
- MCP input_schema passthrough defaults to `{"type":"object","properties":{}}` when absent
  (api/mcp_client.py:141) - avoids the OpenAI "object schema missing properties" 400 class
  (https://github.com/openai/openai-agents-python/issues/449).
