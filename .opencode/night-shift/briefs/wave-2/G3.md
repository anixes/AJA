## Findings

### G3-F1 — CRITICAL — Discord never subscribes to the event bus; in standalone gateway mode it receives ZERO telemetry/approvals
- **Files**: `gateway/adapters/discord_adapter.py:405-409` (`_subscribe_bus_events`) — **defined but never called** (verified by repo-wide grep: the only reference is the definition itself; `start()` at :80-123 never invokes it).
- **Trace**:
  - TelegramAdapter subscribes to every bus event in `start()` (tg_client.py:104-107). DiscordAdapter has the machinery (`_make_event_handler` → `_put_telemetry`) but nothing wires it.
  - The bus→LanceDB bridge (`runtime/lancedb_logger.py:35` singleton) is imported ONLY by `runtime/autonomous_loop.py:8`.
  - **Standalone mode** (`python -m aja.gateway.server` via daemon_manager / server.py): autonomous_loop is never imported → `lancedb_logger` singleton never instantiated → NOTHING journals bus events → Discord's `_poll_lancedb_events` sees only rows written by other writers (tracker.log_event etc.) → mission progress, MISSION_COMPLETED research reports, and **AWAITING_APPROVAL escalation events never reach Discord**.
  - **`aja serve` mode**: works only incidentally (autonomy component imports the logger), and even then Discord gets events ~1s late through the DB poller instead of the intended direct fan-out.
- **Impact**: Approval keyboards never appear on Discord in daemon deployments → stranded missions awaiting an approval nobody saw. Contradicts the class docstring "Functional parity with TelegramAdapter" (discord_adapter.py:29).
- **Fix**: call `self._subscribe_bus_events()` in `DiscordAdapter.start()` (one line), mirroring tg_client.py:104-107; unsubscribe already handled in `stop()` (:165-174).

### G3-F2 — HIGH — Approvals CAN be dropped despite the "never dropped" guarantee (two leak paths)
The comment on both `_put_telemetry` implementations says *"Approval requests are never dropped"* (tg_client.py:287, discord_adapter.py:443). Two paths break it:
1. **Drop-oldest can evict an approval**: the AWAITING_APPROVAL fast path sheds `q.get_nowait()` — whatever is oldest, *including another AWAITING_APPROVAL* (tg_client.py:292-298, discord_adapter.py:446-455). A burst of N>1000 pending approvals guarantees evictions; more realistically, a saturated queue where the head happens to be an older approval loses it silently.
2. **Fan-out stage has NO approval protection at all**: `_dispatch_telemetry` does bare `chat_q.put_nowait(ev)` and on `QueueFull` drops **any** event including approvals, logging only (tg_client.py:338-344, discord_adapter.py:498-505). A tailed chat whose sends stall (network outage → `send_failures` climbing, tail loop sleeping 1s between errors) fills its 500-slot chat queue → every subsequent approval for that chat is dropped → mission stranded with no operator surface.
- **Pattern reference**: priority-aware load shedding — high-priority items must evict *low-priority* items specifically, and drops must be counted as metrics, not just logged ([Backpressure Handling](https://vabs.github.io/2026/06/11/data-pipeline-backpressure-handling): overflow-policy table + "silent drops without metrics" anti-pattern; [bounded queue patterns](https://www.application-architect.com/posts/python-asyncio-queues-producer-consumer-pattern)).
- **Fix**: scan-for-lowest-value victim in the shed path (skip AWAITING_APPROVAL victims), and give chat queues the same protected-enqueue helper used on the shared queue. Add `events_dropped` / `approvals_dropped` counters to metrics.

### G3-F3 — HIGH — Slack telemetry pipeline is a dead end: tails hang forever, nothing ever feeds them
- **File**: `gateway/adapters/slack_adapter.py:127-155`
- **Trace**: `start_tail` creates `_chat_queues[chat_id]` + a `tail_events` task consuming from it. But SlackAdapter has **no dispatcher, no bus subscription, and no LanceDB poller** — nothing in the entire codebase puts anything into a Slack chat queue (grep confirms: only `tail_events`' own `setdefault`). Orchestrator's MISSION branch calls `slack.start_tail(chat_id)` happily (orchestrator.py:628-629), the task starts, blocks on `chat_queue.get()` forever, and the user is told "I'll live-report any progress" (orchestrator.py:624).
- **Impact**: Slack missions report success but deliver zero telemetry and zero approval prompts (Slack also has no approval-button path at all). Pure silent feature death — worst kind, because nothing errors.
- **Fix options**: (a) minimal parity — subscribe Slack to bus events with a dispatcher like TG/Discord; (b) honest contract — make orchestrator reply "telemetry tails unsupported on this platform" when the adapter lacks the full pipeline; (c) route through the LanceDB poller pattern. Council should pick; (a) matches the Phase-7 parity intent.

### G3-F4 — HIGH — Per-chat tail registration leaks + resurrection blocker (`active_telemetry_bridges` never cleaned)
- **Files**: `gateway/orchestrator.py:627-632`, `tg_client.py:313-329`, `discord_adapter.py:472-490`, runner `stop()/start()`.
- **Trace**:
  - **No per-chat unsubscribe exists anywhere.** Once a chat missions once, its `_tail_tasks` entry + 500-slot `_chat_queues` entry persist until adapter `stop()`; `_dispatch_telemetry` fans every event to every historical chat forever (unbounded growth on long-lived VPS processes with many chats; also wasted puts to dead chats).
  - **Resurrection blocker**: `active_telemetry_bridges` (orchestrator.py:56) is added at :632 and NEVER removed — not on `GatewayRunner.stop()` (which cancels tails and clears adapter state), not on adapter restart. If adapters are ever restarted in-process (runner.stop→start, future reconnect logic), a returning MISSION from a known chat hits `if chat_id not in self.active_telemetry_bridges` → False → `start_tail` skipped → **that chat's telemetry is permanently dead** while the system believes it's tailed.
  - Minor asymmetry: tg `stop()` cancels `_tail_tasks` inline (:151-153) but never clears `_chat_queues` (only `stop_tails` does); Discord's stop delegates to `stop_tails()` which does both.
- **Fix**: remove chat from `active_telemetry_bridges` in a `stop_tail(chat_id)` API called from adapter teardown; evict idle chat queues (LRU or last-event timestamp TTL).

### G3-F5 — MEDIUM — `_poll_adapter` crash is PERMANENT death (answers the L74 question) and health snapshots lie afterwards
- **File**: `gateway/gateway_runner.py:69-80`
- **Answer**: Yes — permanent. The outer `except Exception` at :79-80 logs `"Poll loop crashed for {adapter}"` and the coroutine returns; the task is gone. There is no supervisor, no retry, no restart anywhere (grep: nothing re-creates `_poll_adapter` tasks outside `start()`). Worse:
  - `adapter.is_running` remains `True` → `get_health_snapshot()` (tg :616, discord :699) reports a healthy running adapter while its poll loop is dead → Docker healthcheck (`aja healthcheck --quick`) and any monitoring see green.
  - The adapter's internal tasks (dispatcher, LanceDB poller, PTB polling) keep running as zombies consuming events nobody dispatches to a consumer — inbound `_queue` grows unboundedly (command queues are deliberately unbounded, tg :48-50).
- **Trigger realism**: any non-Exception-subclass escape aside, a single unexpected error inside the adapter generator (e.g., a library raising after partial teardown) kills the platform until full process restart.
- **Fix**: wrap the `async for` in a restart-with-backoff loop (respecting `is_running`), mark `is_running=False` on final death, and feed a degraded-health flag into the snapshot. Cite: [asyncio docs — save task references / lifecycle](https://docs.python.org/3/library/asyncio-task.html#create_task); [strong-ref set + done-callback supervision pattern](https://mkennedy.codes/posts/fire-and-forget-or-never-with-python-s-asyncio/) and [GC'd mid-flight tasks under load](https://baodev.studio/blog/asyncio-create-task-garbage-collected/) (the crashed task here is properly referenced in `_tasks`, so this is restart policy, not GC risk).

### G3-F6 — MEDIUM — daemon_manager: watchdog promised in docstring doesn't exist; double-start TOCTOU; orphaned children on partial failure
- **File**: `gateway/daemon_manager.py`
- Items:
  1. **No watchdog** despite the header "Auto-restart watchdog supervision" (:7). If the gateway or worker child dies, nothing restarts it and nothing notices. Restart storms are therefore impossible — but so is resilience; docstring is false advertising.
  2. **Double-start race**: `start_daemon` does `get_status()` → spawn ×2 → `write_text(pid_file)` (:58-104) with no lock. Two concurrent invocations (CLI + orchestrator `_auto_boot_local_worker`, which A1 noted is sync-in-async) both read "stopped" and both spawn. The second gateway exits via server.py's `acquire_lock("gateway")` refusal — but the second WORKER also holds `acquire_lock("worker")`… leaving a confusing half-alive process set and a pid_file whose pids point at whichever write landed last; `stop_daemon` may then miss the first pair's pids entirely.
  3. **Partial-spawn orphaning**: if the worker `Popen` raises (env/path issue), the function propagates BEFORE writing the pid file (:85-104) → the gateway child runs orphaned, invisible to `get_status`/`stop_daemon` until process reboot.
  4. **PID-reuse false positive (Windows)**: `_is_process_running` treats ANY live pid as the daemon (:140-145, STILL_ACTIVE check) — after reboot/pid recycling, `get_status` reports "running", refuses legitimate starts. No process-name/started_at corroboration.
  5. `stop_daemon` fires SIGTERM/taskkill and immediately unlinks the pid file without waiting for exit → an immediate `start_daemon` can race the dying children (ports/locks still held).
- **Fix**: O_EXCL lockfile around start; write pid file after EACH successful spawn (or pre-register); verify process identity beyond pid existence; wait briefly for termination in stop.

### G3-F7 — MEDIUM — serve.py composition: early-return teardown nukes the whole process; components started but partially un-stoppable
- **File**: `runtime/serve.py:84-189`
- Items:
  1. **Second-instance refusal = full shutdown**: `run_gateway()` returns normally (not raising) when `acquire_lock("gateway")` fails (server.py:14-19). `asyncio.wait(..., FIRST_COMPLETED)` then treats it as a completed child → finally-block cancels autonomy AND stops the scheduler → `aja serve` silently becomes a no-op that exits cleanly whenever another gateway instance holds the lock (e.g., leftover daemon from daemon_manager). Operator sees "[*] AJA serve stopped cleanly." — maximally misleading.
  2. **`run_gateway` never receives `stop_event`**: signal-driven shutdown relies on task cancellation into `await stop_event.wait()` inside server.py:38; that works, but server.py's OWN signal handler (`handle_exit`, server.py:32-34) sets a local event nobody else knows about — two independent stop mechanisms coexist; only cancellation path is exercised under serve. Fragile but currently functional; flagged for the composition owner.
  3. **Workflow job re-registration**: `scheduler.add_job(goal=..., workflow_name=...)` runs on EVERY boot (:154-161). Briefing jobs are documented idempotent; whether `add_job` dedupes by `workflow_name` was not verified in this pass — if not, every `aja serve` restart accumulates duplicate scheduled jobs (restart storm amplification). Needs a quick confirmation by whoever owns cron_scheduler.
  4. Positives for the record: scheduler.stop_async awaited in finally; file_watcher.stop() is sync-safe (automation/file_watcher.py:114); signal restorers handle POSIX/Windows split correctly; child-crash propagation and error logging during gather are correct.
- **Fix**: distinguish "gateway exited: lock held" (log loud warning, keep serving autonomy OR exit nonzero) from crash; thread `stop_event` into run_gateway; verify/ensure workflow add_job idempotency keyed on workflow_name.

### G3-F8 — LOW/MEDIUM — Metrics/health inconsistencies across the telemetry pipeline
- **Files**: `tg_client.py:239-240,57-69,616-621`; `discord_adapter.py:258-259,62-74,699-704`
- Items:
  1. `queue_size`/`queue_lag_seconds` measure ONLY the inbound command `_queue` and are refreshed only when a user message arrives — the entire outbound telemetry pipeline (shared queue depth, per-chat queue depths, dispatcher lag) is invisible to `get_health_snapshot()`. Under G3-F2-style stalls, monitoring shows zeros.
  2. Drop events (QueueFull in `_put_telemetry` and `_dispatch_telemetry`) log warnings but bump **no counter** — total silent loss is unmeasurable. ("Silent drops without metrics" anti-pattern: https://vabs.github.io/2026/06/11/data-pipeline-backpressure-handling)
  3. Discord simulated-fallback sets `is_running=True` (discord_adapter.py:93) with no pipelines started — snapshot claims healthy while nothing polls/dispatches; `start_tail` later lazily spawns a dispatcher (:477-480) creating divergent lifecycle states depending on call order.
  4. `seen_event_ids` trim `set(list(seen)[-4000:])` (tg :494-495, discord :685-686) — Python sets are unordered, so the slice evicts an ARBITRARY 4000/5000, not the oldest → recently-seen IDs can be evicted while stale ones persist → occasional duplicate deliveries after each trim.
- **Fix**: expose per-stage queue depths + dropped counters in snapshots; use an OrderedDict/deque for seen-ID eviction; gate `is_running` in fallback mode.

### G3-F9 — LOW — Wave-1 `_event_lock` consequence: global head-of-line blocking across ALL platforms (design watch-item)
- **File**: `gateway/gateway_runner.py:99-106`
- Not re-reporting the race fix (A1-F3) — but note the chosen remedy serializes `handle_gateway_event` (multi-second LLM turns) across every chat on every platform. One slow mission-intent turn now delays ALL platforms' message handling (telemetry tails unaffected — separate tasks). The AdapterProxy swap is redundant UNDER the lock (lock alone already prevents clobbering); passing `responder=adapter` explicitly into `handle_gateway_event` would allow removing the global lock and restoring concurrency. Flagging so the council consciously accepts or revisits the throughput tradeoff.
