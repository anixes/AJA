Scope: `aja/orchestration/gateway.py` (chat retries, backoff, 4xx fast-fail, copilot 401 refresh-retry), `aja/orchestration/providers/openai_compat.py` (+ google/anthropic adapters for contract comparison), `aja/llm.py` error paths, callers of `gateway.chat` that mishandle None/"".

## Findings

### F1. CRITICAL — No per-request timeout on the OpenAI SDK clients: worst-case ~90 min silent hang per logical LLM call
- **File:line**: `libs/aja-core/aja/orchestration/gateway.py:279-283` (`_get_openai_client` — no `timeout=` kwarg); `providers/openai_compat.py:151-155` (`_get_client` — same).
- **Description**: The openai-python SDK defaults to `DEFAULT_TIMEOUT = httpx.Timeout(600, connect=5.0)` and `DEFAULT_MAX_RETRIES = 2`, auto-retrying connection errors, 408, 409, 429 and ≥500 internally (verified against `src/openai/_constants.py` and README — see R1). Neither AJA client passes `timeout` or `max_retries`. So one `gateway.chat(retries=3)` call = up to 3 outer × 3 inner attempts × 600 s ≈ **90 minutes** wedged before returning None. During that window the worker turn, DirectSession turn, or cron tick is blocked (and per A2-F2/F4 the loop itself can be blocked by sibling paths). aiohttp paths are better but inconsistent: gateway's own session has `total=60` (:252) while `google_adapter._get_session` (:72-75) and `anthropic_adapter._get_session` (:42-51) build bare `ClientSession()` → aiohttp default total=**300 s** (R3). Anthropic then loops `retries=3` over it → 15 min.
- **Proposed fix**: pass explicit `timeout=<env-tunable, e.g. httpx.Timeout(120, connect=5)>` and `max_retries=0` (AJA owns retry policy; see F3 amplification) to every AsyncOpenAI construction; add `aiohttp.ClientTimeout(total=...)` to both adapter sessions matching the gateway's 60 s posture.

### F2. HIGH — Dual retry layers amplify attempts ~3× (retry-storm class), with two unsynchronized backoff schedulers
- **File:line**: gateway.py:636 + openai_compat.py:206 (`client.chat.completions.create` inside AJA's own retry loops); gateway legacy loop :378-690; openai_compat loop :203-263.
- **Description**: AWS guidance is explicit: "retry at one layer only", because per-layer retries multiply amplification (N layers × R retries each ⇒ R^N attempts; see R2, R4). AJA currently stacks: SDK internal retries (2) × adapter/gateway retries (3) × caller-level repair/recovery rounds (`llm_structured.structured_completion` max_repair=1 extra round-trip on ANY failure incl. provider outage — llm_structured.py:220-230 sends a "repair" prompt for what is actually a network failure; swarm `_planning_recovery_ladder` adds more). Under a provider 5xx storm a single planning call can emit dozens of requests. Chat-completions POSTs are stateless so idempotency isn't the hazard here — load amplification and cost are (each retried attempt bills tokens on success).
- **Proposed fix**: set SDK `max_retries=0`, keep exactly one retry loop (adapter level), and make `structured_completion` distinguish transport failure (None/"" response ⇒ raise immediately as provider-outage, no repair round) from validation failure (repair round).

### F3. HIGH — Zero jitter anywhere; deterministic `2**attempt` backoff synchronizes retries across fleet workers
- **File:line**: `gateway.py:690`, `openai_compat.py:263` (`await asyncio.sleep(2**attempt)`); anthropic/google adapters have **no sleep at all** between attempts (anthropic_adapter.py:200-221 tight loop; google_adapter ignores the `retries` param entirely).
- **Description**: All backoff sleeps are unjittered exponential with no cap discussion (`2**attempt`: 2s, 4s under retries=3 — small, but the pattern matters at fleet scale). AJA runs multi-host fleets (baton handover, VPS deploy, cron scheduler firing scheduled research missions on schedules) plus multiple spawned workers per mission sharing one provider quota. When the shared upstream rate-limits, all correlated clients re-fire at identical t+2/t+4 boundaries — the classic thundering herd AWS documents (R2, R4: "if all clients retry at the same time... retries can be ineffective"). Full jitter (`sleep = uniform(0, min(cap, base·2^attempt))`) is the canonical fix (R4).
- **Proposed fix**: shared helper in `aja/utils` (e.g. `async def backoff_sleep(attempt, base=1.0, cap=30.0): await asyncio.sleep(random.uniform(0, min(cap, base * 2**attempt)))`) used by gateway + openai_compat; give anthropic its missing sleep and google its missing retry honoring.

### F4. HIGH — Legacy Copilot Responses path defeats the 4xx fast-fail: deterministic 400s burn all retries silently
- **File:line**: `gateway.py:572-576` (raise site) vs `gateway.py:661-677` (classify site).
- **Description**: Non-200 on `/v1/responses` raises `ValueError(f"Copilot Responses API Error {resp.status}: {detail}")`. That exception carries **no `.status_code`**, so the except-handler's fast-fail probe (`getattr(e, "status_code", ...)` :664-666) returns None and the error is classified RETRYABLE. A deterministic 400 (bad model id, unsupported payload shape, oversized image) therefore retries 3× with sleeps, then hits `if attempt == retries: return None` (:674-675) — the error message (including the provider's diagnostic body) is dropped on the floor: **silent exhaustion with zero user-visible output**. Contrast: the chat-completions branch of the very same method fast-fails correctly via SDK exceptions, and openai_compat fast-fails `(400, 404, 422)` — three different 4xx policies inside one codebase.
- **Proposed fix**: attach status to the raised error (small typed `ProviderStatusError(status, detail)` or `err.status_code = resp.status`), include 402/409 policy alignment with openai_compat, and log-and-surface final failures instead of bare `return None`.

### F5. HIGH — self_healer: un-awaited coroutine + silent-"" file destruction
- **File:line**: `libs/aja-core/aja/utils/self_healer.py:50` then `:58`.
- **Description**: Two compounding bugs. (a) `fixed_code = gateway.chat(MODEL, prompt)` never awaits → `fixed_code` is a coroutine object; `file_path.write_text(<coroutine>)` raises TypeError (coroutine also never awaited → RuntimeWarning; heal feature has likely never worked). (b) If the call were awaited, the modern adapter path of `gateway.chat` returns **`""`** on any provider failure (see F7) → `file_path.write_text("")` would **truncate the production source file to empty**, then health-check fails and it "escalates" having destroyed the file. This is the sharpest concrete instance of the silent-swallow class converting an LLM outage into data loss.
- **Proposed fix**: `run_async_synchronously(gateway.chat(...))`; guard `if not fixed_code: skip file write + log`.

### F6. MEDIUM/HIGH — decision/engine: un-awaited `gateway.chat` makes the Decision Engine permanently fall back
- **File:line**: `libs/aja-core/aja/decision/engine.py:96-102` inside sync `decide()`; swallowed at the broad try → `_parse_and_validate(coroutine)` does `response.strip()` → AttributeError → returns `{"type": "NEW", "confidence": 0.0, "reason": "Parse error: ..."}` (:281-283).
- **Description**: Same un-awaited-coroutine class as F5 but fully silent: every autonomous decision logs a misleading "parse error" and degrades to NEW/confidence-0 without anyone knowing LLM routing was dead. Failure surfaces nowhere actionable (logger.error text blames JSON parsing).
- **Proposed fix**: use `run_async_synchronously(...)` like `decision/evaluator.py:112` already does correctly; add an explicit falsy check distinguishing "no response" from "bad JSON".

### F7. HIGH (contract) — `gateway.chat` returns **None or "" depending on which internal path served the call**: failures become indistinguishable from empty successes
- **File:line**: adapter path `gateway.py:365-373` (`return llm_resp.content or ""` — openai_compat/openrouter/copilot/llama_cpp/ollama/groq/nvidia/together AND google_adapter all registered via `providers/__init__.py`), vs legacy path `gateway.py:646/:672/:675` (`return None`). Adapter failure mode: `openai_compat.chat` **never raises and never returns None** — every timeout/auth-error/exhaustion collapses to `LLMResponse(content="")` (:251, :262, :265), so gateway.chat yields `""`.
- **Description**: Wave-1 established the caller contract "None = exhausted retries" (direct_loop.py:160 checks `if not response`; T2-F5 relies on it). But since the adapter path now serves most providers, real outages surface as `""` — which callers treat as a legitimate empty completion: `plan_gate` safe-default logic, `llm_structured` (burns a repair round prompting against `last_raw=None`), `completion()`'s `or ""` coercion (llm.py:569, :586) makes it permanent. Downstream consumers cannot distinguish "model said nothing" from "provider was down". The three public surfaces disagree: `chat`→None|""|dict, `chat_stream`→yields nothing on failure (fallback swallows the streaming exception at DEBUG, gateway.py:738-739), `completion/completion_async`→always "".
- **Proposed fix**: pick ONE failure sentinel. Recommended: raise typed `ProviderError` from adapters (they have the context), keep `chat`'s None for exhaustion, and delete the `or ""` coercions in llm.py; minimally, make openai_compat return `LLMResponse(content="")` only for genuine empty choices and `None`/raise for transport failure, with gateway translating consistently.

### F8. MEDIUM — Silent swallow instances at callers (each hides provider failure from users)
- **File:line / effect**:
  - `swarm.py:330-333`: if the summarization call fails, `results_str = <None>` → f-string interpolates literal `"None"` and the original >5000-char results are **destroyed**; final synthesis prompt then contains garbage. `final_report = await ...chat(...)`: None report ends the mission logged as "Final Synthesis Complete:\nNone" with success semantics. No falsy check on either call.
  - `interface/tui.py:251-253`: `if not isinstance(response, str): response = ""` — provider outage renders as AJA saying nothing; user gets zero feedback.
  - `automation/context.py:43-47`: `async def llm(...) -> str` annotation lies — returns None on failure (google path) straight into workflow steps that trust `str`.
  - `decision/evaluator.py:169, :295`: `raw = run_async_synchronously(gateway.chat(...))` — raw may be None; downstream JSON-parse fallback masks outage as evaluation failure (same masking pattern as engine.py but at least awaited).
  - Adjacent type-contract bug (route to T-subgroup): `autonomy/reflection.py:77` and `:136` call `self.gateway.chat(prompt, system=...)` positionally binding the *prompt text* into the required `model` slot while leaving required `prompt` unbound → TypeError on every reflection run (caught+logged generically at :38, so skill synthesis silently never happens).
- **Proposed fix**: every call site adopts the same triage: falsy ⇒ log WARNING with provider/model context + propagate typed error or safe-default that is *visible* (never interpolate the failure into the next prompt).

### F9. MEDIUM — Copilot 401 refresh-retry hot-loop twins (adapter path) + non-copilot 401s retried pointlessly
- **File:line**: `openai_compat.py:253-255` (401/403 → `_refresh_copilot_auth()` → `continue`, **no sleep**, bypasses the attempt-exhausted warning); `gateway.py:559-570` (Responses-path twin, also no sleep — corroborates A2-F10, not re-reported as new); `gateway.py:667` excludes 401/403/429 from fast-fail → a plain bad OPENROUTER/OPENAI key (deterministic 401, refresh is copilot-only no-op at :254 returning False → falls through to warn+sleep+retry) burns all 3 attempts over 6 s before surfacing nothing.
- **Description**: If keyring holds a revoked GitHub token, `resolve_copilot_token()` keeps handing back the same stale token → all attempts spin in a network-bound hot loop with no backoff (AWS R2: retries should be dose-limited). Conversely for non-copilot providers a 401 will fail identically forever — pure wasted latency. Note the good part worth preserving: both refresh implementations DO invalidate the cached client (`self._client = None` openai_compat.py:127; `self._openai_client = None` gateway.py:687), so the "retries don't invalidate cached clients" hunt item is satisfied on the copilot path.
- **Proposed fix**: after a refresh-`continue`, still apply (shortened, jittered) backoff; count refresh-attempts separately with a cap (e.g. 1 refresh per call); fast-fail 401/403 when `_refresh_copilot_auth()` returns False.

### F10. LOW — Streaming fallback duplicates partial output; stream errors invisible at DEBUG
- **File:line**: `gateway.py:733-744`; `openai_compat.py:295-308`.
- **Description**: If the SSE stream dies mid-generation (connection reset — llama.cpp keeps generating until socket drop per A2-R3), deltas already yielded reach the consumer, then the catch-all falls back to a full non-streamed `chat()` and yields the complete response again → duplicated prefix in chat/TUI. The mid-stream exception is logged at DEBUG only, so recurring provider instability is invisible in INFO ops logs.
- **Proposed fix**: track whether any chunk was yielded; if so, do NOT fall back (surface error instead); log stream failures at WARNING with redaction.

## Internet research

- **R1. openai-python defaults & APITimeoutError**: `DEFAULT_TIMEOUT = httpx.Timeout(600, connect=5.0)`; `DEFAULT_MAX_RETRIES = 2`; connection errors, 408, 409, 429, ≥500 auto-retried twice with short exponential backoff; timed-out requests retried by default; `APITimeoutError` raised only after retries exhausted. Basis for F1/F2.
  - https://github.com/openai/openai-python/blob/main/src/openai/_constants.py
  - https://github.com/openai/openai-python (README §Retries, §Timeouts)
  - https://github.com/openai/openai-python/blob/main/src/openai/_exceptions.py (`APITimeoutError(APIConnectionError)` — note: subclasses APIConnectionError, so `isinstance(e, APIConnectionError)` checks conflate timeout vs connect-refused)
  - https://github.com/openai/openai-python/blob/main/src/openai/_base_client.py (retry loop reuses an idempotency key across attempts)
- **R2. Retry amplification / single-layer doctrine**: "retry at one layer only"; retries amplify load during overload; backoff alone doesn't reduce long-term work; retry budgets + circuit breakers compose. Basis for F2.
  - https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter (AWS Builders' Center, accessed 2026-08-25)
  - https://brooker.co.za/blog/2022/08/11/backoff.html ("Backoff is not a good retry policy")
- **R3. aiohttp default timeouts**: `ClientTimeout(total=300, sock_connect=30)` session-wide default — basis for F1's adapter-session exposure (300 s × anthropic's 3 attempts).
  - https://docs.aiohttp.org/en/stable/client_quickstart.html#timeouts
  - https://docs.aiohttp.org/en/stable/client_reference.html
- **R4. Jitter best practice**: full jitter (`uniform(0, min(cap, base·2^n))`) is the AWS-recommended default; un-jittered exponential backoff is "the clear loser" — highest work AND longest completion; correlated clients (cron schedules, fleet workers sharing quota) synchronize into herds without it. Basis for F3.
  - https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/
  - https://brooker.co.za/blog/2015/03/21/backoff.html
- **R5. Idempotency framing**: retries are only safe for side-effect-free calls; OpenAI SDK generates an idempotency key reused across ITS retry attempts — relevant to F2 (chat-completions is stateless here; `store: false` set on Responses payloads at gateway.py:537, so duplication risk is cost, not state corruption).
  - https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter

2. **CLAIM(L2-F7)**: One failure sentinel across `chat`/adapters/`completion*`. Blocks: plan_gate safe-default correctness (T2-F5), llm_structured repair economics, all F8 call sites. Needs council ruling: raise-vs-None (T2 council Q2 asked the same for candidates/choices).
3. **CLAIM(L2-F3)**: Shared jittered `backoff_sleep` helper; adopt in gateway + openai_compat; add missing anthropic sleep / google retry-honoring.
4. **CLAIM(L2-F4)**: Typed status-carrying error on the Responses path so the existing fast-fail classifier works; align 4xx policy sets across the three sites (gateway legacy, gateway Responses, openai_compat `_NON_RETRYABLE_STATUS`).
5. **CLAIM(L2-F5+F6)**: Two one-line `await`/`run_async_synchronously` fixes + falsy guards; F5 additionally prevents the ""-wipe file-destruction path.
