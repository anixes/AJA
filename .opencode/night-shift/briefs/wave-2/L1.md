## Findings

### F1. HIGH — Anthropic adapter is broken-by-contract dead code; every "anthropic" call silently degrades to the legacy OpenAI-compat path
- **File:line**: `providers/anthropic_adapter.py:34` (`__init__(self, api_key="")` — **no `base_url` kwarg**); `orchestration/gateway.py:344` (`adapter_cls(api_key=..., base_url=self.base_url or "")` — uniform instantiation); swallowed at `gateway.py:374-375`; registration at `providers/__init__.py:43-47`; `providers.json:10-11` (own comment admits untested).
- **Description**: The gateway instantiates ALL adapters uniformly with `(api_key=..., base_url=...)`. `GoogleAdapter` and `OpenAICompatAdapter` accept both kwargs; `AnthropicAdapter` does not → `TypeError: __init__() got an unexpected keyword argument 'base_url'` on EVERY anthropic call, caught by the broad except and logged only at DEBUG, then falls through to the legacy path. Consequences:
  1. The native Messages-API adapter (prompt-caching `cache_control`, extended thinking) is unreachable — zero instantiation sites exist in the entire codebase (grep confirms).
  2. Even with the constructor fixed, `AnthropicAdapter.chat()` **raises** `RuntimeError` on any ≥400 response (:206-210) instead of returning an empty `LLMResponse` like its siblings (openai_compat.py:251, google_adapter.py:234) — direct drift from the Protocol docstring ("Returns normalized LLMResponse", base.py:54). The adapter-path contract would crash into the same silent fallback.
  3. It also hardcodes `ANTHROPIC_BASE_URL` (:24, :203), ignoring any configured base_url, unlike every other adapter.
  - Meanwhile the legacy path that actually serves anthropic sends `_build_system_message(provider="anthropic")` output — system blocks annotated with `cache_control` (:133-145) — over the OpenAI-compat endpoint; whether the compat layer tolerates `cache_control` there is unverified (no key configured; providers.json self-declares untested).
- **Severity**: HIGH — AGENTS.md Phase 10 claims "anthropic registered"; in reality the registered native adapter can never run, and no test covers either path (no `anthropic` hits under tests/python live conformance beyond the skip-if-unconfigured matrix).
- **Proposed fix**: add `base_url: str = ""` to `AnthropicAdapter.__init__` (defaulting to ANTHROPIC_BASE_URL); make `chat()` return empty `LLMResponse` + non-retryable discrimination like openai_compat; add a unit test asserting `adapter_cls(api_key="x", base_url="y")` succeeds for every class in `_REGISTRY` (a registry-conformance contract test would have caught this instantly).

### F2. HIGH — Copilot 401-refresh destroys the operator's env-var token permanently (`os.environ.pop`) — auth death spiral on VPS/docker deployments
- **File:line**: `copilot_auth.py:149-155` (`invalidate_copilot_cache()` does `os.environ.pop("COPILOT_GITHUB_TOKEN", None)`); triggered from `gateway.py:566`, `gateway.py:683`, `openai_compat.py:123`.
- **Description**: When the raw GitHub token was sourced from `COPILOT_GITHUB_TOKEN` / `GH_TOKEN` / `GITHUB_TOKEN` (the documented docker/VPS path — `.env.vps.example` injects env vars, and `config.py:15` runs `load_dotenv(override=True)` at import), the FIRST 401/403 erases `COPILOT_GITHUB_TOKEN` from the process environment. `resolve_copilot_token()` then finds nothing: keyring absent on headless Linux (see R3), gh CLI absent in containers → returns `("", "")`. Every subsequent refresh is a no-op while retries keep using the same expired JWT until exhaustion → Copilot is dead for the remainder of the process (`aja serve` = process-lifetime). The pop also mutates global state other components may rely on.
- **Repro sketch**: container with only `COPILOT_GITHUB_TOKEN` set; let the ~30-min Copilot API token expire mid-mission (R1: TTL ≈ 25–30 min); observe one refresh cycle, then permanent "" resolution.
- **Proposed fix**: never mutate `os.environ` in invalidate; track the resolved source and re-read the original source instead. Optionally cache-and-restore: keep the raw token in module state (not environ) keyed by source.
- **Adjacent race (same lines)**: `invalidate → resolve → exchange` has no lock/singleflight. N concurrent workers hitting expiry each invalidate (clearing fresher caches written by peers), each re-exchange against `api.github.com/copilot_internal/v2/token` — thundering herd against a rate-limited endpoint, plus last-writer-wins on `_CACHED_RAW_TOKEN`/`_jwt_cache`. A `threading.Lock` (or asyncio singleflight) around resolve+exchange fixes it cheaply.

### F3. MEDIUM/HIGH — No timeouts anywhere in the adapter layer; hung providers stall missions 5–10 min per attempt (×retries)
- **File:line**: `providers/openai_compat.py:151-155` (`AsyncOpenAI(...)` without `timeout=`); `gateway.py:279-283` (same); `providers/google_adapter.py:72-75` (`aiohttp.ClientSession()` — default total=300s); `providers/anthropic_adapter.py:42-51` (same); contrast `gateway.py:252` which *does* set `ClientTimeout(total=60)` for its own session.
- **Description**: openai-python's default request timeout is **600 s** (`Timeout(connect=5, read=600, write=600, pool=600)` — R2). With the gateway default `retries=3`, a wedged llama.cpp server or black-holed cloud connection blocks a worker turn for up to ~30 min with zero AJA-level cancellation. aiohttp paths fare marginally better (300 s library default) but are still implicit, undocumented, and unconfigurable — there is no `AJA_LLM_TIMEOUT_S` knob anywhere (grep: none). This is exactly the failure mode nanobot had to patch (R2, issue #3455).
- **Proposed fix**: explicit `timeout=float(os.getenv("AJA_LLM_TIMEOUT_S", "120"))` on AsyncOpenAI construction (both sites) and `ClientTimeout(total=...)` on both aiohttp adapters; document the knob next to `AJA_WORKER_TIMEOUT_S`.

### F4. MEDIUM — Proxy/SSL behavior is asymmetric across the two HTTP stacks: httpx paths honor proxy env vars, aiohttp paths silently ignore them
- **File:line**: `providers/openai_compat.py` + `gateway.py:_get_openai_client` (httpx via AsyncOpenAI — `trust_env=True` default → honors `HTTP(S)_PROXY`, `SSL_CERT_FILE`); vs `google_adapter.py:74`, `anthropic_adapter.py:44`, `gateway.py:254` (bare `aiohttp.ClientSession` — `trust_env=False` since 2017, maintainer-confirmed won't change — R4).
- **Description**: Behind a corporate proxy (or mitm-proxy SSL inspection via `SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`-style env config), OpenAI/OpenRouter/Copilot-chat-completions traffic routes through the proxy while Google Gemini, Anthropic, and the Copilot Responses-API traffic (`gateway.py:556`, uses `_get_session`) attempts direct egress and fails with connection errors that look like provider outages. No AJA-level proxy option exists for either stack. This produces maddening "half the providers work" reports.
- **Proposed fix**: pass `trust_env=True` to all three ClientSession constructions (opt-in via env `AJA_TRUST_ENV=1` if the secure-default concern matters), and document parity in VPS.md.

### F5. MEDIUM — Base-URL handling: no `/v1` validation for OpenAI-compat endpoints; misconfiguration degrades to silent empty responses
- **File:line**: `providers/openai_compat.py:60-68` (rstrip ok, no `/v1` heuristic); `PROVIDER_BASE_URLS` defaults are fine, but user-supplied `base_url` (via `LLMGateway(base_url=...)` / `llm.py` config paths) flows straight through; AsyncOpenAI appends only `/chat/completions` — no automatic `/v1` (R2 convention).
- **Description**: A user configuring `LLAMA_CPP_URL=http://localhost:8080` (missing `/v1`) or a custom gateway without the suffix gets 404s. In `chat()` a 404 is in `_NON_RETRYABLE_STATUS` (:51) → returns `LLMResponse(content="")` after ONE attempt with only a logger.error — callers treat empty content as "model said nothing" (plan_gate safe-default, worker retry ladder), so the root cause is invisible unless DEBUG logging is on. Same class for trailing-slash double-slash variants (rstrip handles those) and for `ollama` URLs missing `/v1`.
- **Proposed fix**: warn-once heuristic when an OpenAI-compat base_url doesn't end in `/v1` (excluding known exceptions like copilot root and localhost servers that serve both); consider surfacing non-retryable-404 as a distinct typed error rather than empty-string success shape.
- **INFO adjacent**: `gateway.py:548` builds `{base}/v1/responses` for copilot while chat-completions lives at `{base}/chat/completions` (no `/v1`) — inconsistent prefix conventions against the same host; unverifiable without a key, worth one live check when Copilot access exists.

### F6. MEDIUM — `BaseModelProvider.chat_completions` implementations ignore the `tools` parameter entirely and leak whole gateways per call
- **File:line**: `api/interfaces.py:10-17` (abstract signature advertises `tools`); all five impls — `llm.py:206-240` (Google), :247-282 (OpenAI), :289-324 (OpenRouter), :331-366 (LlamaCpp), :372-462 (Copilot) — accept `tools` and never forward it to `gw.chat(...)`.
- **Description**: Two contract drifts. (1) Any consumer routing tool-calling through `provider_registry`/`completion(tools=...)` gets text-only responses forever — tool_calls can never appear in the returned `{"choices": [...]}` shape, silently (no error, no warning). (2) Each call constructs a fresh `LLMGateway(...)` (:216, :258, :300, :342, :436) and drops it unclosed — recreating the exact per-call socket-leak family Wave 1 fixed inside `gateway.chat()`, but one level up where the fix doesn't reach. Also note they poke the private `gw._google_generate_content` (:225).
- **Proposed fix**: forward `tools` (and map tool_calls back into the choices dict); reuse cached gateways via `get_gateway_for_model` instead of raw construction.

### F7. LOW/MEDIUM — entry_points discovery runs as an import-time side effect with print-based failure reporting
- **File:line**: `llm.py:493-512` (`discover_providers()` executed at module import :512).
- **Description**: (a) Import-time plugin loading means any broken third-party package in group `aja.model_providers` slows or noises every `import aja.llm` (failures `print()`ed at :508, bypassing logging config that isn't set up yet). (b) The Python <3.10 branch imports `importlib_metadata`, which is not a declared dependency — on such interpreters the outer bare `except Exception: pass` (:509) silently disables discovery with no signal. (c) Discovery is never re-invoked after installs. Project targets Python ≥3.11 (quickstart gate), so (b) is dead-code risk rather than live bug.
- **Proposed fix**: make discovery lazy/explicit (call from `get_gateway()` first use), route failures through `logger.warning`, drop the <3.10 branch.

### F8. LOW — Keyring fallback chain is solid, but Windows backend degradation is invisible and `load_dotenv(override=True)` can resurrect stale tokens
- **File:line**: `copilot_auth.py:50-76` (`_keyring_get/_set` swallow all exceptions at debug level — correct); `config.py:15` / `main.py:13` (`load_dotenv(override=True)`).
- **Description**: The get/set wrappers handle the documented headless failure modes (NoKeyringError, missing pywin32 → WinVault unavailable, R3) correctly — resolution falls through to env/gh CLI as designed. Two residual nits: (1) when keyring write fails during device-flow login, success is reported with only a debug-level trace — the operator believes the token is vaulted while it lives solely in ACL'd plaintext `.env`. A single `logger.warning("keyring unavailable; token stored in .env fallback only")` would close the gap. (2) `override=True` means a rotated token exported as a fresh `COPILOT_GITHUB_TOKEN` env var is silently shadowed by the stale `.env` copy until the file is edited — surprising during incident response.
- **Checked clean**: `migrate_token_to_keyring` idempotence (:253-265); HMAC-free baton scope not applicable here; `_jwt_cache` fingerprinted by SHA-256 prefix (:394-397) so multi-token sessions don't cross-contaminate; exchange timeout=10s present (:400-427).

## Internet research

- **R1. Copilot API token semantics**: short-lived bearer (~25–30 min TTL) obtained by exchanging the raw GitHub OAuth token at `GET api.github.com/copilot_internal/v2/token`; must be refreshed proactively or long-running sessions die with 401s; exchange response carries `endpoints.api` (Business/Enterprise hosts differ from api.githubcopilot.com) and identity headers (`Editor-Version`, `Copilot-Integration-Id`) are validated server-side.
  - https://github.com/openclaw/openclaw/issues/31132 (100% repro >25-min sessions without proactive refresh)
  - https://github.com/anomalyco/opencode/issues/20759 (raw ghu_ tokens rejected; exchange mandatory; `endpoints.api` ignored = Business plan breakage)
  - https://deepwiki.com/hadi2f244/freegpt/4.2-copilot-internal-api ; https://lzwjava.github.io/github-copilot-auth-en
  - *AJA implication*: `exchange_copilot_token` honors neither `endpoints.api` nor proactive refresh-before-expiry — it relies purely on reactive 401 handling, which F2 shows is destructive. `copilot_request_headers` does send the identity headers correctly.
- **R2. OpenAI SDK defaults & base_url convention**: default timeout is 10 minutes (`Timeout(connect=5, read=600, ...)`); `base_url` is used verbatim (only `/chat/completions` appended — no auto-`/v1`); empty-string base_url env traps are a known SDK bug class.
  - https://developers.openai.com/api/reference/python (Timeouts section: "By default requests time out after 10 minutes")
  - https://github.com/HKUDS/nanobot/issues/3455 (identical bug: AsyncOpenAI without timeout hangs up to 600s)
  - https://github.com/openai/openai-python/issues/2927 (base_url verbatim-use pitfalls)
- **R3. keyring backends**: Windows needs WinVaultKeyring (pywin32/win32ctypes required; absent → `RuntimeError: No recommended backend was available`); headless Linux raises NoKeyringError without D-Bus/SecretService — both raise, both correctly swallowed by AJA's wrappers.
  - https://github.com/jaraco/keyring/issues/207 ; https://keyring.readthedocs.io/en/latest (headless section) ; https://stackoverflow.com/questions/44643443/
- **R4. aiohttp trust_env**: proxy env vars ignored by default (`trust_env=False` since 2017); maintainers explicitly refuse to change the default (2025-10) — applications must opt in per-session.
  - https://docs.aiohttp.org/en/stable/client_advanced.html#proxy-support ; https://github.com/aio-libs/aiohttp/issues/10682 (maintainer refusal quote)
