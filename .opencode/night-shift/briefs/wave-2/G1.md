## Key architectural fact governing severity

The Envelope adapters (`TelegramEnvelopeAdapter`, `DiscordEnvelopeAdapter`) are the designated
replacement surface per their module docstrings ("Intended to replace tg_client.py after the
migration window") and are unit-tested (`tests/python/unit/test_telegram_envelope.py` incl. the
streaming throttle test at :217) — but **nothing in production calls `send_envelope()`** and
**nothing emits `Kind.STREAM_CHUNK`** (repo-wide grep: only envelope.py's own factory and the
adapter branch). Likewise `completion_stream`/`chat_stream` have exactly one consumer chain
(llm.py:589→603) with zero downstream callers. The entire streaming pipeline is **dormant
migration code**: findings below are latent-but-live the moment wiring happens, which is
precisely when they'd be hardest to debug.

## Findings

### F1 — HIGH — The "streaming edit circuit breaker" claimed in AGENTS.md does not exist; edit failures retry forever with no RetryAfter handling
- **Files**: `adapters/telegram_envelope.py:219-245` (`_handle_stream_chunk`)
- **Evidence**: AGENTS.md Phase 15 states "Telegram envelope: streaming edit errors caught with
  circuit breaker". `_handle_stream_chunk` contains **zero** try/except around either
  `send_message` (:229) or `edit_message_text` (:238). Repo-wide grep for circuit/breaker/
  RetryAfter/retry_after in gateway/: **no hits** (only presence/agent_loop.py has an unrelated
  mission-loop breaker). Git history confirms no such code was ever committed to this file.
- **Repro**: start a stream → user deletes the Telegram message mid-stream → every subsequent
  chunk raises `BadRequest: message to edit not found`; exception escapes `send_envelope` into
  whatever drives envelopes; buffer keeps growing; nothing recovers. Same for 429
  `RetryAfter` (PTB raises typed `telegram.error.RetryAfter` with `.retry_after` — ignored) and
  400 "message is not modified" (reachable when a chunk appends empty text → identical edit).
- **Why it matters once wired**: STREAM_MIN_INTERVAL_SECONDS=1.0 (:37, :234) matches the ~1
  msg/sec per-chat guidance, but edits share the chat quota with the concurrently-running
  telemetry tail sends (`tg_client.tail_events` → `send_notification`) — burst overlap ⇒ 429,
  which is currently unhandled anywhere in the streaming path.
- **Fix**: wrap send/edit in error-tolerant loop: on `RetryAfter` sleep `e.retry_after`; on
  "message not found"/"message is not modified"/parse errors reset `state["message_id"]=None`
  (rotate to fresh message); trip a per-key breaker after N consecutive failures that stops
  editing but keeps buffering; reconcile AGENTS.md claim.

### F2 — HIGH — No 4096-char guard anywhere in Telegram delivery; long streams AND long final replies are silently lost
- **Files**: `adapters/telegram_envelope.py:224,229,238-242` (monotonically growing buffer sent
  whole on every edit); legacy live path `tg_client.py:556-579` + `orchestrator.py:706`
- **Detail**: Telegram rejects text >4096 chars with 400 TEXT_TOO_LONG (editMessageText and
  sendMessage alike). In `_handle_stream_chunk` the buffer only ever grows, so the first chunk
  crossing 4096 makes **every subsequent edit fail permanently** (feeds F1's no-breaker loop).
  On the *live* non-streaming path today: `send_message` catches all exceptions and returns None
  after logging (`tg_client.py:574-579`), so any orchestrator response >4096 chars (long mission
  reports/synthesis are realistic) is **silently dropped — the user gets nothing**, and the
  response is still appended to history (:719-725).
- **Fix**: stream path: rotate a new message each 4096 chars (keep tail window in one editable
  message). Legacy path: split on boundaries or truncate-with-notice before sending; never let
  send-failure be fully silent for final replies.

### F3 — MEDIUM-HIGH — `chat_stream` fallback duplicates content after partial yield
- **File**: `orchestration/gateway.py:692-744`
- **Trace**: chunks are yielded inside the try (:734-736). Any exception mid-stream (provider
  connection drop mid-generation is routine) is caught at :738 with a debug log, control falls
  out of the provider block, and the **non-streamed fallback re-runs the whole completion and
  yields the FULL text again** (:742-744). Consumers concatenating yielded chunks display half an
  answer followed by the complete answer from the start.
- **Repro**: point llama_cpp/OpenAI-compatible endpoint at a proxy that resets connections under
  load; observe duplicated responses.
- **Fix**: track `yielded_any`; if True, do NOT fall back (optionally yield a truncation marker);
  fall back only when zero chunks were produced.

### F4 — MEDIUM — Stream-state leak + cross-turn bleed onto old messages
- **File**: `adapters/telegram_envelope.py:78,220-222,133`
- **Trace**: `_stream_states` is keyed `correlation_id or chat_id` and pruned ONLY in `stop()`
  (:133). Two failure modes: (a) unbounded growth — one entry per conversation/correlation on a
  long-running `aja serve` process; (b) bleed — STREAM_CHUNK envelopes constructed manually
  without correlation_id key on chat_id, so a *new* turn in the same chat keeps **editing the
  previous turn's message** instead of starting a fresh one (classic stale-text bug; the test at
  test_telegram_envelope.py:222 always passes correlation_id, hiding mode b).
- **Fix**: require correlation_id for stream keys; prune state on terminal envelope or TTL sweep;
  cap dict size.

### F5 — MEDIUM — DiscordEnvelopeAdapter advertises `streaming_edit=True` with dead throttle field but implements NO stream path
- **File**: `adapters/discord_envelope.py:34,95,170-193`
- **Trace**: capabilities report `streaming_edit: True` (:34,:109) and `self._stream_throttle`
  (:95) exists but is referenced nowhere. `send_envelope` has no `Kind.STREAM_CHUNK` branch — a
  chunk would fall through to `channel.send(env.text)` :187, i.e. **one Discord message per
  token-chunk**. discord.py queues and sleeps through rate limits rather than erroring (see
  research §3), so the symptom would be the channel's entire REST activity stalling for minutes
  via pre-emptive rate limiting — sends, tails, approvals all frozen — plus notification spam.
  Contrast: the legacy wired adapter (`discord_adapter.py`) correctly does whole-message delivery
  only.
- **Fix**: implement a real coalescing edit path (≤1 edit/sec/channel, matching the shared
  send+edit bucket) or set `streaming_edit=False` and have ConversationCore coalesce before
  calling; delete the dead field either way.

### F6 — MEDIUM — MarkdownV2 auto-parse_mode with zero escaping = guaranteed 400s and silent message loss
- **File**: `adapters/telegram_envelope.py:144-148` (render) feeding `send_message` :169-182
- **Trace**: `render()` sets `parse_mode=MarkdownV2` from capabilities whenever `env.meta["markdown"]`
  is truthy. The applied `MobileMDRenderer.render()` converts tables but **escapes none of the 18
  MarkdownV2 reserved chars** (`_ * [ ] ( ) ~ \` > # + - = | { } . !`), and LLM output routinely
  contains unclosed `*`/backticks. Result: 400 "can't parse entities" (incl. the classic "Can't
  find end of the entity starting at byte offset N") → caught in `send_message` → returns None →
  **total silent loss of the reply**. Note the internal inconsistency too: the streaming preview
  path (:229/:238) sends WITHOUT parse_mode while the final reply would use it — formatting flips
  mid-conversation even when both succeed.
- **Fix**: drop auto-MarkdownV2 (plain text, like every other path in this repo) or adopt a real
  markdown→MarkdownV2 converter; never set parse_mode without context-aware escaping.

### F7 — LOW-MEDIUM — Unguarded callback `answer()`/edits can strand missions in AWAITING_APPROVAL
- **Files**: `tg_client.py:510,531,542`; same shape `adapters/telegram_envelope.py:313-315`;
  contrast guarded `discord_adapter.py:319-322,351-356`
- **Trace**: `await query.answer()` runs BEFORE `resolve_approval`. PTB raises
  (`QueryIsTooOld`/"query is too old and response timeout expired", webhook timeouts) when the
  button press arrives >~10s after render or is answered twice — the exception aborts the handler
  BEFORE approval resolution, leaving the mission stranded though the operator pressed Approve.
  Also `edit_message_text(text=message)` at tg_client.py:542 is unguarded: an idempotent
  double-click returning identical text triggers 400 "message is not modified"; deleted/too-old
  messages raise similarly (escapes into PTB's error handler — noisy, and the operator sees
  nothing). Discord edits are wrapped, but failure leaves stale buttons visible with zero user
  feedback (debug log only).
- **Fix**: wrap answer() (proceed to resolution regardless of answer success); wrap edits with
  "not modified"-tolerance; on Discord edit failure send a follow-up channel notice.

### F8 — LOW — MobileMDRenderer partial-table / pipe-prose edge cases
- **File**: `render.py:24-26,63-89`
- **Detail**: `_is_table_row` treats ANY line containing `|` as a table row, so prose lines with
  pipes following a separator-looking line get absorbed and mangled into bullets. A table split
  across streaming boundaries (header+separator arrived, rows pending) renders as raw lines first
  then flips format once rows arrive (only relevant if F-fixes ever route buffers through the
  renderer mid-stream — currently it is applied only at send time on full text, where this is
  cosmetic).

### Verified-clean (for the record)
- `presenter.py` — console-only persona rendering; no streaming involvement; neutral-prompt logic
  sound.
- `render.py` fast paths (`'|' not in text or '-' not in text`) guard the common case cheaply.
- `discord_adapter.py` approval interaction edits — properly try/except-wrapped (residual UX gap
  noted in F7 only).
- Throttle clock injection (`_clock`) in telegram_envelope is test-friendly and race-free within
  a single consumer (matches A1's verified-clean note on `_stream_states` single-consumer use).

## Internet research

### 1. Telegram editMessageText rate limits & flood control
- Official Bot FAQ guidance (cited verbatim by multiple 2026 trackers): ~**1 msg/sec per chat**
  (short bursts tolerated, then sustained 429s), **20 msg/min per group**, ~**30 msg/sec global
  bulk**; **every API method counts**, explicitly including `editMessageText`:
  - https://core.telegram.org/bots/faq (canonical)
  - https://www.conferbot.com/limits/telegram (verified 2026-08-20 table + FAQ quotes)
  - https://botnamefinder.com/blog/telegram-bot-rate-limits-explained (per-scope table; "A bot
    that sends a message, edits it, and answers a callback is consuming 3 API calls")
- Empirical edit-specific data: burst test reports **429 after ~33 edits in 1s**; community
  consensus that `edit_message_text` needs LONGER pauses than plain sends:
  - https://fyw-telegram.com/blogs/1650734730 (FAQ Q3: "Does editing a message consume quota? Yes,
    editMessageText counts 1 unit")
  - https://stackoverflow.com/questions/31914062/... (comment: "The problem was only associated
    with messages, the content of which I tried to change… take more pause between messages")
- Contract: 429 carries machine-readable `parameters.retry_after`; correct behavior is sleeping
  EXACTLY that long for that request (retrying early extends penalty); PTB surfaces it as typed
  `telegram.error.RetryAfter.retry_after`:
  - https://www.conferbot.com/errors/telegram/429-too-many-requests-retry-after
- Hard limits relevant to F1/F2: `text` must be 1–4096 chars (400 TEXT_TOO_LONG); empty strings
  rejected; also documents "message not found", "can't parse entities", 403 blocked-bot as
  editMessageText outcomes needing distinct handling:
  - https://gramio.dev/telegram/methods/editmessagetext

### 2. Telegram MarkdownV2 partial/unescaped-text pitfalls
- 18 reserved characters must be escaped outside entities (`_ * [ ] ( ) ~ \` > # + - = | { } . !`);
  ONE unescaped dot rejects the WHOLE message; escaping rules are context-sensitive (code blocks
  escape only backtick/backslash; URLs only `)`/`\`), so a global escaper corrupts code fences —
  relevant to why MobileMDRenderer cannot simply be patched with a blanket regex:
  - https://md2tg.projectstain.dev/guides/telegram-markdownv2-escaping
  - https://botnamefinder.com/blog/telegram-markdownv2-escape-characters
- The unclosed-entity variant ("Can't find end of the entity starting at byte offset N") is
  documented as **common specifically for bots piping AI-generated markdown** — precisely AJA's
  use case; recommendation for LLM output is conversion, not parse_mode:
  - https://md2tg.projectstain.dev/guides/telegram-cant-parse-entities
- Practical escape-function references (PTB ships `telegram.helpers.escape_markdown(version=2)`):
  - https://stackoverflow.com/questions/73142803/telegram-api-markdownv2-escape-characters-bug
- No official "partial-text leniency": Telegram validates the ENTIRE submitted string each call —
  a streamed prefix containing one unbalanced `*` fails that edit (and every subsequent edit
  until the balancing char arrives), validating the hunt concern about mid-stream markdown
  breakage for any future parse_mode-on-stream design. (Implied by the whole-message validation
  model documented at the two md2tg guides above.)

### 3. Discord rate-limit buckets for message edits
- Sending and editing **share the same per-channel rate-limit bucket**; discord.py pre-emptively
  sleeps (no exception) when a bucket exhausts — Rapptz: "There is no special casing of this
  endpoint so any wait time is probably due to pre-emptive rate limit handling":
  - https://github.com/Rapptz/discord.py/issues/6073
- Pre-emptive waits do NOT raise; they stall the caller (interaction tokens expire during long
  waits); `Client(max_ratelimit_timeout=...)` exists since v2.0 to bound it:
  - https://github.com/Rapptz/discord.py/issues/9073
- Library handles 429 automatically (queue + sleep + retry) — hand-rolled retries make congestion
  worse; tight-loop message edits are THE canonical self-inflicted flood ("update once a second
  or slower"); repeated INVALID requests (not rate) trigger the temporary connection ban:
  - https://client.falixnodes.net/guides/troubleshooting/discord-rate-limits
- Net for F5: a naive per-chunk `channel.send` wouldn't error — it would silently freeze all
  channel activity through bucket queuing, which is worse operationally than a crash.

## Council questions

1. **Dormancy vs priority**: the envelope adapters are tested-but-unwired. Should F1/F4/F5/F6 be
   fixed now (cheap, small surface, tests exist) or formally recorded as a "wiring gate
   checklist" attached to whichever PR connects them? Fixing now avoids shipping the migration
   with known landmines.
2. **AGENTS.md integrity (F1)**: Phase 15 documents a streaming-edit circuit breaker that was
   never committed. Reverted, lost, or written against an unmerged branch? Who owns reconciling
   doc claims against code before more agents trust AGENTS.md as ground truth?
3. **>4096 policy (F2)**: split messages, truncate with notice, or file-upload fallback for long
   reports? This is a product decision affecting both adapters and possibly TUI parity.
4. **Stream lifecycle**: there is no STREAM_END/finalize kind — previews linger and the final
   reply duplicates the preview text. Should the final reply DELETE the preview (deleteMessage /
   message.delete()) upon completion, or should the final edit BE the completion (no separate
   final message)? Determines whether F4's pruning hook is a terminal-envelope handler.
5. **F3 contract**: when a stream dies mid-flight after partial output, should consumers see
   (a) silence + error event, (b) explicit truncation marker chunk, or (c) best-effort resync?
   The eval harness (Phase 9) may have expectations about turn outputs — coordinate.
