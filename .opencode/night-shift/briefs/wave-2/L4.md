## Findings

### F1 — CRITICAL, silent drop: ConversationCore never sees attachments
`core/conversation.py::handle()` reads only `msg.text` (line ~197); `InboundMessage.attachments` has **zero** consumers in the file (verified via grep). The envelope Telegram adapter dutifully downloads photos to base64 `Attachment.data` (telegram_envelope.py:295-305) and Discord envelope builds image Attachments (discord_envelope.py:46-48), but on every surface that routes through ConversationCore the image is discarded and the model answers text-only. Today this bites REPL/file_watcher; if serve.py ever switches adapters to the envelope stack, Telegram/Discord photos go silently blind. Same class of bug: orchestrator `_chat_via_core` (orchestrator.py:750-760) constructs an InboundMessage with no attachments even though it was called precisely because... actually it's the non-image branch — but the asymmetry shows the core API simply has no image channel. **Recommend**: add `image_urls` to ConversationCore intake → direct-loop prompt.

### F2 — HIGH, silence on provider rejection: no capability-aware fallback anywhere
If the active model/endpoint can't accept images, `completion()` at orchestrator.py:203 has no try/except; the exception propagates through `handle_gateway_event` (no guard around line 700-706) and `gateway_runner.process_event` (no try) to `_poll_adapter`'s blanket handler (gateway_runner.py:72-76) which only logs. **User gets total silence** after sending a photo. There is no vision-capability probe and no "I can't see images" message anywhere in the codebase. The deterministic-4xx no-retry policy makes this a fast silent death rather than a hang. **Recommend**: wrap the image-bearing chat call, emit "⚠️ Current model X cannot process images" on 400-class image errors; optionally maintain a per-model `images_in` capability flag (the Envelope `PlatformCapabilities.images_in` field exists but is decorative).

### F3 — HIGH, silent drop: Slack has NO image support at all
`slack_adapter.py:89-99`: file_share/photo messages with empty text are dropped at the adapter ("Dropping message without text"). Images sent as Slack files never become MessageEvents. No warning is sent to the user — invisible failure. Comment acknowledges the design ("no media is attached on Slack") but nothing tells the *user* their photo was ignored. Also `slack_envelope` doesn't exist; slack has no envelope parity.

### F4 — MEDIUM, dead code + unbounded disk cache: VisionBridge
`gateway/vision.py::VisionBridge` is instantiated once (orchestrator.py:67) and **never called** — `describe_image` returns a placeholder string "[AJA Vision Bridge ... pending VLM connection]" and would actively degrade UX if wired. `download_and_describe` writes every image to `DATA_DIR/gateway/cache/images/` with no eviction/cap. Either wire it as the fallback describer for non-vision models (ties into F2) or delete it.

### F5 — MEDIUM, payload bloat & persistence: full base64 data URLs in session store
Both live adapters inline the whole image as a base64 data URL into `media_urls` (tg_client.py:216-218, discord_adapter.py:226-228). Orchestrator stores it verbatim in `session["last_image_url"]` (orchestrator.py:460) and `update_session` JSON-dumps the entire session — including the multi-MB data URL — into the LanceDB `session_json` cell on EVERY turn (persistence.py:83; called twice per event: orchestrator.py:487 and :725). A 10 MB Telegram photo → ~13.7 MB base64 → rewritten to storage on each subsequent message until evicted. No size cap check exists before download either (Telegram getFile caps at exactly 20 MiB = 20,971,520 B — larger files fail with 400 "file is too big"; Discord allows up to 10 MB non-boosted / 25 MB boosted uploads). **Recommend**: cap pre-download via `photo.file_size`, store images out-of-band (cache dir + ref key in session), and strip `last_image_url` from persisted JSON.

### F6 — LOW/MEDIUM, fragile follow-up heuristics for last_image_url TTL
- Reattach trigger is a hardcoded English keyword tuple (orchestrator.py:463-466); ANY other text clears the image context (:471-473). "what did I just send?" or non-English follow-ups silently lose the image. Multi-image events keep only `media_urls[0]`.
- 24h TTL (orchestrator.py:476-480) computes `max(h["time"])` over history — works, but history rows store TEXT ONLY (`{"role","text","time"}` at :482-484): the assistant/model never sees prior turns' images even within TTL; each follow-up rebuilds a single-image prompt from the heuristic. Multimodal conversation memory effectively doesn't exist.
- If a PHOTO event routes to intent MISSION (route_intent has_image hint at :581), the image is silently dropped from the mission goal too.

### F7 — LOW, provider-path gaps (non-Copilot)
- **Google/Gemini** (`orchestration/gateway.py:88-113`): `_flatten_google_content` explicitly drops `image_url` parts (logged only). Gemini supports inline_data vision via generateContent — the capability exists upstream but AJA discards it; user gets text-only answer about a photo they sent (silent wrongness).
- **openai/openrouter/etc. direct chat-completions**: content lists pass through unchanged, so vision works where the model supports it — but no capability gate, so non-vision models → 400 → F2 silence.
- **llama.cpp local worker**: llama-server DOES support OpenAI-compatible vision via `--mmproj` (base64 data URLs and remote image_url both accepted on `/v1/chat/completions`; capability discoverable via `/models` "multimodal" flag) — but AJA's dual-model worker path never sends images (worker missions get text goals only), so local vision is unused capacity. Also `chat_stream` (gateway.py:692-744) passes list content through for SDK providers (OK) but its copilot branch uses chat.completions which rejects images → exception → debug-logged fallback to `chat()` (works, but invisible behavior divergence).
- **Copilot Responses conversion detail**: assistant multimodal history converts only `type=="text"` parts (gateway.py:468-476) — image parts in PRIOR assistant/user turns are silently dropped when building Responses `input_items` (only the forced current-turn routing keeps images; historical images are lost across turns — consistent with F6's no-multimodal-history finding).

## Internet citations

- OpenAI image input requirements (Responses + Chat Completions): PNG/JPEG/WEBP/non-animated GIF; up to **512 MB total request payload**, up to 1500 images/request; base64 data URLs supported — https://developers.openai.com/api/docs/guides/images-vision and API reference `input_image` (image_url = fully qualified URL or base64 data URL) — https://developers.openai.com/api/reference/resources/responses/methods/create/
- Telegram Bot API: bot **downloads capped at 20 MiB (20,971,520 B)** — getFile returns 400 above it; sendPhoto accepts ≤10 MB photos — https://core.telegram.org/bots/api ; boundary-exact measurements: https://charliemorrison.dev/blog/telegram-bot-api-file-size-limits/
- llama.cpp server vision: OpenAI-compatible `/chat/completions` image input (base64 data URL or http(s) URL) enabled via `-hf` auto mmproj or `--mmproj FILE`; `/models` exposes `multimodal` capability; malformed/non-image inputs return non-200 — https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md , PR https://github.com/ggml-org/llama.cpp/pull/12898 , server README https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md
